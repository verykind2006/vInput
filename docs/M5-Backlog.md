# M5 待办

M4 期间发现、决定留到 M5 一并处理的问题。写在这里而不是留在对话里——
M5 开工时应当先读这份。

---

## 一、注入延迟偏长（用户明确提出）

**现象**：说完话到文字出现在光标处，用户反馈「时间稍微有一点点长」。

**实测拆解**（2026-08-15，Qwen3-4B-4bit + Whisper large-v3-turbo）：

```
16:24:02  松开语音键
16:24:09  文字出现        总 7.1 秒（转写 2.1 + 校正 5.0）

16:24:31  松开
16:24:36  文字出现        总 5.1 秒（转写 1.1 + 校正 4.0）

16:26:15  松开
16:26:25  文字出现        总 10.0 秒（转写 1.9 + 校正 8.0 超时放弃）
```

**转写 1–2 秒，校正 4–8 秒——校正是大头。**

### 一个必须先排除的干扰

上面这批数字是在**后台有另一个进程反复加载 Whisper 跑实验**时测的，
两者抢同一块 GPU。同一天更早、干净环境下测的是 **1.88–2.33 秒**
（见 `CorrectionPipeline.init` 的注释，8 秒预算就是据此定的）。

**所以 4–8 秒里有多少是干扰、多少是模型本身，尚未确定。M5 动手前
必须在干净环境下重测一次**，否则会在被污染的数据上做取舍。

### 可选的方向（未决）

| 方向 | 收益 | 代价 |
|---|---|---|
| 缩短校正提示词 | 预填充变快，可能省 1 秒以上 | 现在的六百多字是实测调出来的，负例全靠它才不乱改（曾出现 `小米遥控器→小米耀空气` 被应用），缩短有回退风险 |
| 降低 `maxTokens` | 略快 | 已从 256 压到 96，余量不大 |
| 校正改为「后台跑，下次生效」 | 注入零延迟 | 违背「同一句话开关能看出差别」的验收标准，且用户拿不到本句的校正 |
| 按句长决定要不要校正 | 短句快 | 长句恰恰更需要校正 |
| 就让用户按需开关 | 零成本 | 已经可行（菜单一键），但等于承认默认体验不够好 |

**注意**：不能走「先注入原文、校正完再替换」——替换已注入的文本需要选中
并重打，跨应用极不可靠，且违反规则三（注入前校验目标应用未变）。

**M5 的场景润色才是完整方案**，按前台应用切换风格（原始设计文档规则一）：

## 四、校正与润色是否合并成一次推理——**暂缓，需专项**

**动机**：校正已占约 2 秒，再叠一层润色就是两次 LLM 调用。合并能省一半。

**为什么暂缓**（2026-08-15 决定）：合并会让 M4 最重要的安全机制作废。

拼音闸门能工作，是因为校正的输出是**「原文→替换」的同音清单**，机器可以
逐条验证。而润色必须改读音（加标点、去口水词、改书面语），合并之后输出的
是一整段改写过的文本，**闸门无从下手**。

这个风险在 M4 是实测发生过的，不是假想：

- 模型建议过 `小米→米粒`、`情况→状况`、`优化优化→优化方案`
- 某一版提示词让 `小米遥控器→小米耀空气` **真的被应用了**（同音，闸门放行）

没有闸门，这些会直接落到用户的文字里。

**动手的前提**：先有一套能替代拼音闸门的安全机制。可能的方向——长度比例
约束、要求模型同时输出「改了哪几处」供逐条校验、保留原文一键回退、
HUD 显示改动供确认。**方案明确之前不要合并。**

## 五、先评估转写层余量，再决定润色层投入

M4 收尾时六段标准测试（用户读固定文本，正确答案已知）的错误归因：

| 用户说的 | 转写出来的 | 错在哪层 | 下游能修吗 |
|---|---|---|---|
| 代码**里**有个问题 | 代码有个问题 | 转写漏字 | ❌ |
| 上**线**计划 | 上**限**计划 | 转写（同音） | ✅ |
| 会议室见**面** | 会议室见 | 转写漏字 | ❌ |
| **比如**说 | **比方**说 | 转写换词 | ❌ |
| **Claude Code** | **collodecode** | 转写听错 | ❌ |
| **GitHub Actions** | github actions | 转写丢大小写 | ❌ |
| 权限**配置** | 权限 | 转写漏字 | ❌ |

**七个错误里只有一个是下游能修的。**

根本原因：**下游看不到音频。** Whisper 一旦写出「collodecode」，声学证据就
没了，任何 LLM 都无从知道用户说的是「Claude Code」——只能靠上下文猜，
而「不许猜」正是拼音闸门存在的全部意义。漏字更彻底：字压根没进入文本，
下游连「这里少了东西」都不知道。

**在转写层不够好的时候做润色，等于在一段已经错了的文字上精修排版。**

### 待测：large-v3 vs turbo

`vendor/models/openai_whisper-large-v3` **已经下好在本地**，当前跑的是
`turbo`（速度优化版，准确率低于 large-v3）。

用户当初试过 large-v3 后选了 turbo，理由是「整体体验效果不好」——但**那是在
还没有校正层、注入延迟只有一两秒的时候做的决定**。现在链路上已经花着数秒
在校正，large-v3 多出的转写时间占比完全不同。

**若 large-v3 本来就不会把「Claude Code」听成「collodecode」，这个错误根本
不需要下游去修。**

测法：同一批音频（`/tmp/vinput-bench/` 已有基准集）两个模型各跑一遍，
数错误数与耗时。菜单里能换模型，成本很低。

其他待评估的转写层余量：`DecodingOptions` 的温度回退策略、beam search
参数、技术词 initial prompt（进行中）。

## 六、质量瓶颈已从校正层转移到转写层

M4 收尾时的真机数据显示，**剩下的错误大多是校正层从设计上就修不了的**：

| 真机错误 | 性质 | 校正能修吗 |
|---|---|---|
| 上线 → 上限 | 同音 | ✅ 能修但漏了（4B 的能力问题） |
| Claude Code → collodecode | 非同音 | ❌ 拼音闸门不放行 |
| GitHub Actions → 全小写 | 大小写 | ❌ |
| 「见面」→「见」、漏「配置」 | 漏字 | ❌ |

校正层只处理同音替换，这是它安全性的来源，也是它能力的边界。

**M5 规划时应当重新评估**：继续在润色层投入，还是先挖转写层的余量
（换 Whisper 模型、调参数、prompt 工程）。M4 期间给转写加 initial prompt
的收益（标点 0→7）远大于校正层同期的收益（六段测试修对 1 次）。
