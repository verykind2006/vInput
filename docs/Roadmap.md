## 与原始设计的差异及理由

**原 M4「润色层」收窄为「校正层」，润色并入后续。**
润色的正确答案依赖场景——同一句话在 Cursor 里该保留术语原文，在微信里该保留
口语感。脱离场景做，会做出一个后续必须推翻的东西。

**原 M5「场景风格」顺延，M5 改做转写质量。**
M4 收尾的真机数据：六段标准测试**七个错误只有一个是下游能修的**，其余全是
转写层的漏字、听错、大小写；而下游看不到音频，声学证据已经没了。在转写层
不够好的时候做润色，等于在一段已经错了的文字上精修排版。

**M7 蓝牙鼠标插在 M6 与润色之间**（2026-08-16 决定）。

## M6 稳固化（精简版）

**2026-08-17 决定：M6 只做可靠性，分发相关的功能推到 M9。**

理由：产品目前只有一个用户（作者本人）且已在日常使用。设置界面、onboarding
这类是「准备给别人用」才需要的，而「用着用着话就没了」是每天都在发生的。
先把可靠性做到位，分发的需求等真要分发时也会更清楚。

### 四项（按现状核实过，不是照抄原设计）

**⓪ 超过约 30 秒的语音被静默截断（2026-08-17 用户报告，日志已确认）**

**这是主路径上的静默丢字，优先级高于下面四项。**

真机证据，session 103：

```
16:03:17.983  遥控器语音键按下，开始录音
16:03:27.926  ATVV MIC_EXTEND request      ← 三次续期
16:03:37.926  ATVV MIC_EXTEND request
16:03:47.926  ATVV MIC_EXTEND request
16:03:49.421  遥控器语音键松开，进入转写
16:03:59.679  本次能量：304 个块 超阈值 145 个 (47%)
16:03:59.679  注入成功 文本(81字): …我在想,有没有可能把 M8 的分场景优化改成?
```

**31.4 秒只出 81 字，且断在半句上**——「改成**?**」后面没了。按用户基准集
实测语速 3.1–4.6 字/秒，31.4 秒应有 100–140 字，**丢了 20–35%**。

同一批短录音全部完整：18.8 秒→63 字（句号收尾）、11.7 秒→46 字、8.6 秒→25 字。
**分界线在 30 秒附近**（当时以为是单解码窗口的长度，实测是 VAD 分块的
触发点，见下）。

**基准集查不出这个问题**：23 条里最长的「长句与标点」类是 15–30 秒，
**恰好顶到边界但从不越过**。基准集在 30 秒以上零覆盖，这是 M5 度量能力的
一个盲区。

#### 已复现并定位（2026-08-17，`./scripts/long-audio.sh`）

原先列的两个待验证机制**都不是主因**，主因是第三个：
**VAD 分块把连续语音切在句子中间，切中的那一块整块被判死。**

链条（全部走生产 `WhisperKitTranscriber`，turbo，探针实测）：

1. `WhisperKit.swift:1021` 只在 `音频长度 > windowSamples`（= 30 秒）时才
   启用 `chunkingStrategy: .vad`。**30 秒的分界线来自这里**，不是解码窗口。
2. `VADAudioChunker.splitOnMiddleOfLongestSilence` 在后半段找最长静音取中点。
   一口气说完、句间没有停顿时，那个「最长静音」就落在句子中间。
3. 每块**独立**走一遍 `runTranscribeTask`，各自退火，块与块之间没有上下文。
   切在句中的那块开头，模型接不上前文。
4. `firstTokenLogProbThreshold = -1.5`（`Configurations.swift:215`）：首个采样
   token 的 logProb 低于它就整窗作废（`Models.swift:367` 把它列为第一优先的
   `needsFallback`）。实测那一块的首 token logProb = **−1.86**。
5. 六档温度依次失败后，`decodeWithFallback` **不保留过程中最好的一次**，
   只返回最后一次。最后一次恰好又是「首 token 太低、零个 token」那种，
   于是**整块 15.6 秒的语音变成空字符串**——不报错、不记日志。

一段 31.0 秒 / 148 字的实测退火全过程：

```
temp 0.0  首 token −1.86 < −1.5  → firstTokenLogProbThreshold，采样 0 个 token
temp 0.2  采样 92 token          → avgLogProb −11.37 < −1.0，logProbThreshold
temp 0.4  采样 156 token 撞满 224 上限 → avgLogProb −2.28，logProbThreshold
temp 0.6  采样 74 token，内容其实是对的 → avgLogProb −1.074，差 0.074 没过
temp 0.8  首 token −3.05         → firstTokenLogProbThreshold，采样 0 个 token
temp 1.0  首 token −2.89         → 温度用完，就用这一次的结果 → 整块空
```

**它是间歇性的**：同一段音频、同一个模型、温度 0，连续跑 8 次
**3 次丢、5 次正常**；换一轮又是 4/5、0/5。Core ML 在 ANE 上的浮点抖动
足够让 −1.86 在 −1.5 阈值两侧来回。这解释了为什么用户不是每次都撞上，
也解释了为什么单跑一次的测试会报绿。

**临时关掉 VAD 分块，同一段音频 0.554 → 1.000**（CER 0.50 → 0.014）。
不分块时走 Whisper 原生滑窗：窗口解到 27.82 秒的**句子边界**，下一窗从那里
续上，永远不会在句中冷启动。VAD 分块把这个机制拆掉了。

现象数据（生产默认 prompt，覆盖率 = 实际字数 / 参考字数）：

| 语料 | 11–26 秒 | 31 秒 | 43 秒 | 60 秒 | 88 秒 |
|---|---|---|---|---|---|
| 带停顿（4.0 字/秒） | 0.98–0.99 | 0.99 | 0.99 | 1.00 | 1.00 |
| 一口气说（4.8 字/秒） | 1.00 | **0.50**（间歇） | 0.95 | 0.97 | 0.98 |

**丢失量不随时长单调增长**——它取决于切点落在哪里，31 秒那条最容易翻车，
43/60/88 秒反而没事。这否掉了「块数随时长增长、丢失量随之增长」的推断。

#### 原先那两条假设的实测结论

**1 秒悬崖：真实存在，但量级解释不了 20–35%。** 两处 `windowPadding` 确实
各砍掉末尾 1 秒，但 `findSeekPointAndSegments` 通常把 seek 直接推到块尾，
循环自然结束，实测没有因此丢字。上限是每块末尾 ≤1 秒。

**224 token 硬上限：成立，已量化，但真人语速下还没踩到。**
`prefillDecoderInputs` 把 prompt 拼进 `initialPrompt`，`TextDecoder.swift:685`
在 `currentTokens.count >= 223` 处硬停，两者共用同一份预算：

| prompt | prefill token 数 | 每窗可采样 | 24 秒 180 字 | 27 秒 206 字 |
|---|---|---|---|---|
| P6 现行（124 字） | 67 | **156** | 0.883 | 0.772 |
| P0 旧版（63 字） | 40 | 183 | 1.000 | 0.913 |
| 不挂 prompt | 4 | 219 | 1.000 | 0.976 |

这一格是**确定性**的，不像上面那条要靠运气。但要撞到它得 7.6 字/秒——
真人上限 4.6 字/秒 × 30 秒 ≈ 140 字 ≈ 145 token，**在 156 的预算内，
余量约 10 个字**。所以：**P6 没有造成用户遇到的那次截断，但它把余量从
27 个字压到了 10 个字**，说话再快一点、或者再加长 prompt 就会踩上。

`sampleLength` 调大没有用——`loopCount` 取 `min(…, maxTokenContext - 1)`，
224 是 KV cache 的编译期尺寸，改不动。

#### 修法已选定：关掉 VAD 分块（2026-08-17，`./scripts/decode-sweep.sh`）

**最对症的那个修法本轮不可用**：`decodeWithFallback` 每轮覆盖
`decodingResult`、返回最后一次而非最好的一次，改它要动
`vendor/WhisperKit`，而 `vendor/` 在 `.gitignore` 里——改了不进版本库、
换机器就没、而且没人看得见。所以只在 `DecodingOptions` 这几个旋钮里选。

**争议点从来不是「哪个能治丢字」，而是「代价是多少」**：候选里三个动的
都是防幻觉机制。因此对照必须同时量三维——长语音丢不丢字、静音会不会
冒话、日常语料退不退化。**只报一维等于没测。**

每个变体相对现状**只动一处**（组合变体另列），dense-31 每档重复 12 次
（该 bug 是间歇性的，单次结果没有意义），静音/底噪每档 24 次：

| 变体 | dense-31 失败 | 长语料失败 | 静音非空 | 基准集 CER |
|---|---|---|---|---|
| 现状（vad on，首 token −1.5） | 4/12、6/12 | 6/37、8/37 | 0/24、0/24 | 0.0190 |
| **关 VAD 分块（已采纳）** | **0/12、0/12** | 2/37、2/37 | **1/24、0/24** | 0.0190 |
| 关首 token 阈值 | 0/12 | 2/37 | **12/24** | 0.0190 |
| 首 token 阈值放宽到 −3.0 | 0/12 | 2/37 | **10/24** | 0.0190 |
| 关分块 + 关首 token 阈值 | 0/12 | 2/37 | **16/24** | 0.0190 |
| 关首 token 阈值 + 不退火 | 0/12 | 2/37 | **12/24** | 0.0190 |
| 空块救援（见下） | 0/12 | 2/37 | 2/24 | 0.0190 |

（两个数的格子是两轮独立采样。「长语料失败」里恒定的那 2/37 是 budget-24
与 budget-27，属于 224 token 预算那条**另一个**确定性问题，与本条无关。）

**四个候选都能把 dense-31 打到 0/12，区别全在代价。** 动
`firstTokenLogProbThreshold` 的三档把静音幻觉从 0 拉到 10–16 次，漏出来的
正是这个产品一直在防的那一类：「谢谢大家。」「好,谢谢。」，以及
「请不吝点赞 讨订阅 转发 打赏支持明镜与点点栏目」。**那是拿一种丢字换
另一种丢字。** 关分块两轮只漏 1 次「谢谢。」，是唯一便宜的。

**实测掉的两个顾虑**（`./scripts/decode-sweep.sh --scaling`）：

```
3min  176.8s   on 27.6s (6.4x)   off 25.2s (7.0x)
6min  353.6s   on 57.3s (6.2x)   off 59.1s (6.0x)
10min 618.8s   on 111.1s (5.6x)  off 109.8s (5.6x)
峰值：整个测试进程 maximum resident set size 669 MB、peak footprint 48 MB
```

**耗时与内存都没有差别。** 这一条反直觉，值得记住原因：分块那条路把各块
丢进 `TaskGroup` 并发解码（`WhisperKit.swift:803-870`，macOS 上 16 个
worker），不分块走串行滑窗，**看代码会以为长录音要变慢**。实际不会——
ANE 是一块硬件，并发 worker 照样在它上面排队，并行度买不到吞吐。
内存也不涨：mel 与 encoder 都在窗口循环内部逐窗算
（`TranscribeTask.swift:114-146`），整段驻留的只有原始 float 数组。

**方法论上踩到的一个坑，别再踩**：M5 那套静音素材里 `silence30` 恰好是
30.0 秒，而分块的触发条件是「严格大于 30 秒」（`WhisperKit.swift:1021`），
**拿它比较分块 on/off，两边跑的是同一条代码路径**。本轮补了 45 秒静音与
底噪、以及「真人说 14.7 秒 + 尾部静音 20 秒」这个生产上最常见的形态。

#### 这张表的分辨力：静音那一维有效样本是 8 不是 24（独立验收 2026-08-17）

**别把「关分块 1/24 对 0/24」读成 4% 的代价。** 六条静音素材里只有两条
真正能分辨分块开关：

| 素材 | 时长 | 超过 30 秒？ |
|---|---|---|
| `silence05` / `noise02` | 1.5s / 2s | ❌ |
| `silence30` / `noise30` | **恰好 30.0s** | ❌（触发条件是**严格大于**） |
| `silence45` / `noise45` | 45s | ✅ |

本轮补了 45 秒那两条是对的，但**旧的四条没有被剔出分母**——它们在分块
on/off 两边跑的是同一条代码路径。真实读数是 **1/16 对 0/16**（两轮合计）。

**表里还藏着一个被稀释掉的真信号。** 变体「关首 token 阈值」（vad=on）与
「关分块 + 关首 token 阈值」是全表唯一一对只差 `vadChunking` 的变体，
它们的泄漏明细：

```
vad=on    noise02×4  noise30×4  silence45×4              = 12/24，noise45 = 0/4
vad=off   noise02×4  noise30×4  silence45×4  noise45×4   = 16/24，noise45 = 4/4
```

多出来的 4 次**全部来自 `noise45`**，0/4 → 4/4 完全翻转，泄漏内容是
「用转发 打赏支持明镜与点点栏目。」。

**结论：VAD 分块确实在「超过 30 秒的底噪」上压着这类幻觉，这个作用是真的。**
采纳档之所以只漏 1 次，是因为 `firstTokenLogProbThreshold = -1.5` 顶在
前面——而 ⓪ 这个 bug 本身证明的恰恰是**这道闸在阈值附近会因 ANE 浮点
抖动来回翻**。

**这是采纳「关分块」的一个已知代价**：长录音 + 环境噪声这条路上，现在
只剩一道会抖的闸。不足以推翻决定（代价仍远小于动阈值那三档），但因此
`TranscriptCleaner` 那条频道套话规则从「第二道」变成了**最后一道**——
已按数促销词的方式重写（提交 `9f53067`）。

#### 备胎：空块救援（不碰 vendor 地「保留最好的一次」）

已实现但**默认关闭**（`DecodeTuning.rescueEmptyChunks`）。留档是因为它
回答了一个看上去不可能的问题：那个丢弃发生在私有的 `decodeWithFallback`
里，但**被丢弃的东西是一整块，而分块机器全是公开的**——
`VADAudioChunker`（`open class`）、`chunkAll`、`EnergyVAD`、`AudioChunk`、
`transcribe(audioArray:audioArrayOffset:decodeOptions:)` 都是 public。

于是照抄 `WhisperKit.swift:1021-1046` 的参数（`maxChunkLength =
featureExtractor.windowSamples`、默认 `windowPadding` 16000、默认
`EnergyVAD`）在我们这一层自己切一遍，逐块解码，**块的边界就落进了我们
自己的代码**，能在拼接之前看见每一块的结果。某块解出空文本时，只对那一块
用 `firstTokenLogProbThreshold: nil` 重解一次。

**便宜在那道闸**：重试还要求这一块的 `EnergyVAD` 活跃帧占比 ≥ 10%
（真人说话实测约 47%，纯静音是 0）。静音块解出空是**正确答案**，永不重试，
所以默认路径上每一道防幻觉机制都原样保留。每次救援都记日志——原本的失败
形态是「不报错、不记日志、话就没了」，这正是它难查的原因。

**没有采纳它，是因为对照表里它并不比关分块更好**（静音 2/24 对 1/24），
而它多一条自己维护的分块代码路径。若将来关分块出现别的副作用，它是现成的
第二方案。

回归测试留在 `Tests/vInputTests/LongAudioTests.swift`，门控同 `BenchRunnerTests`
（标记文件，不进日常 `./scripts/test.sh`）：

```bash
./scripts/long-audio.sh          # 约 10 分钟，报告出到 Bench/long-audio.txt
```

**dense 组报绿不等于修好了**——失败率两到八成，判「修好」要三个变体
连续两轮零失败；budget 组是确定性的，一次红就是红。

顺带把 30 秒以上的真人样本补进 manifest（需用户补录），堵住基准集这个盲区。

#### 新发现的待办：几分钟量级的录音覆盖率存疑（2026-08-17，未定论）

`--scaling` 那一轮顺带量到的，**不是本条 bug，也还没有定论**：

| 时长 | 分块 on 覆盖率 | 分块 off 覆盖率 |
|---|---|---|
| 3 分钟 | 0.673 | 0.844 |
| 6 分钟 | 0.761 | 0.778 |
| 10 分钟 | 0.664 | 0.521 |

**先说这批数字的局限，它比数字本身重要**：每档**只跑了一次**；音频是把
`dense-91` 首尾相接复制 2/4/7 遍造出来的，**整段是同一段话在重复**，而
`compressionRatioThreshold = 2.4` 恰恰会把「输出太重复」判为失败并触发退火。
也就是说**这个语料在构造上就对 Whisper 不利，绝对值很可能偏悲观**。
**不要把 0.521 当成结论**——要下结论得用不重复的长语料重测，且每档多跑几次。

可达性把这三档分成了两半（已在仓库内核对）：

- 遥控器路径够不到 3 分钟以上：**RC003 固件在整 60 秒切断**，`MIC_EXTEND`
  拦不住（`Testing/M3-Acceptance.md:127` 实测 60.04 秒）。
- 我们自己的上限是 `VoiceSessionKeepalive.maxDuration = 180`（3 分钟）。

**所以 6 分钟与 10 分钟两档是录不出来的场景**，那里 off 输给 on
（0.521 对 0.664）不构成否决关分块的理由。唯一勉强可达的 3 分钟档，
**off 明显更好（0.844 对 0.673）**。而在真实可达范围内（长语料 ≤88 秒），
关分块是 dense 全组 1.000、paced 0.979–0.997。

待办两条：

1. 用**不重复**的长语料把 2–3 分钟这一档重测，每档多跑几次，确认
   0.844 是真的（说满 3 分钟丢约六分之一）还是合成语料的假象。
2. 若属实，Option+D 这条路（遥控器够不着，但键盘够得着 180 秒）应该给一个
   可达的时长上限或临近提示，**而不是让用户在不知情的情况下丢字**——
   这与 M6 ⓪ 本身是同一类问题：静默丢字比报错更糟。

**① 注入失败与目标应用改变 → 剪贴板兜底 + 系统通知**

设计文档规则二、规则三都明确要求「写入剪贴板 + 系统通知」，**两条路都没做**：

- `UNUserNotification` / `NSUserNotification` **全仓零引用**
- `ClipboardSink` 只在「长文本超阈值」这一条路上用；权限被拒
  （`accessibilityDenied`）与目标应用改变时，文本**直接蒸发**

2026-08-17 真机上就撞到过：打包重签名作废了辅助功能授权，
`会话出错：accessibilityDenied`，说的话没落地也没留下副本。

M4 把「说完就切走」的窗口从 1–2 秒拉到 4–10 秒，规则三这条从边缘情形
变成了日常动作。

**用户 2026-08-17 定的**：走**系统通知**（不是只让 HUD 变红）。
理由是规则三触发时用户人已经在别的应用里，HUD 未必在视野内，通知是唯一
还能触达的方式。通知**只提示、不代劳**——文字已在剪贴板，用户自己 Cmd+V。

不做「点通知自动重新注入」：点通知会把 vInput 拉到前台，**反而把注入目标
变成我们自己**，时序脆弱且容易注错地方。

两个连带问题，实现时必须处理：

- **通知要授权，而这是个新弹窗**（与辅助功能不同，不会被重签名作废，
  授权一次长期有效）。若用户拒了或点掉了，这条兜底就静默失效——**而那
  正是本条要修的那类问题**。因此发通知前先查授权状态，**未授权就退回
  HUD 提示并写日志**，不许无声消失。
- **写剪贴板会覆盖用户原有内容**。这是「救回文字」的必然代价，但通知里
  要带上文字开头，让用户知道剪贴板现在是什么。是否改成「仅在剪贴板为空
  或内容是我们上次写的时才覆盖」尚未定——那样更保守，但会出现「既没注进去
  也没进剪贴板」的白救情形。**当前决定：直接覆盖 + 通知告知。**

**② `retry()` 接上 UI 入口**

`Sources/vInput/Transcribe/Transcriber.swift:17` 的注释写着「**目前没有
任何 UI 入口**」——全仓只有测试在调它。转写失败时音频保留了，但用户点不到。
设计文档承诺的「一键重试」缺了一半。

**用户 2026-08-17 定的**：入口放**菜单栏**。理由是状态一直可见、不占用新的
全局快捷键（与现有 Option+D 及其他应用有冲突风险）、也不依赖通知权限
（放通知按钮里的话，通知被划掉入口就没了）。

**③ HUD 标注「本次未校正」**

模型加载中、解析不出替换、被闸门全拦——三种情况用户都只看到「没变化」，
无从判断是哪一种。设计文档规则二的表格本就要求 HUD 标注。
这是上手体验最大的缺口（三轮 QA 里两轮都提了，编号 O1）。

**用户 2026-08-17 定的**：**只分两种**——「模型还在加载」与「已运行但没改动」。

「解析不出替换」是故障，**写日志即可，不打扰用户**：用户对它没有任何可做的
动作，显示出来只会造成疑惑。而前两种的区别对用户是实的——一个能等，
一个是正常工作。

**④ 固定签名身份**

ad-hoc 签名的指纹随二进制变化，每次打包作废辅助功能与输入监控授权。
2026-08-17 一天内坑了三次。`scripts/build-app.sh` 的检测逻辑早已写好，
只差那张自签名证书被标记为可信（需要用户执行一条 `security` 命令，
见 `docs/dev-signing.md`）。

### ⑤ 中文语境下标点是半角（2026-08-17 用户报告）

说中文时输出的是半角 `,`，句号却是全角 `。`。用户希望中文语境用全角标点。
日志里问号同样：`把 M8 的分场景优化改成?`——一句话里两种宽度混着。

**范围（2026-08-17 用户定，先只做逗号、当天扩到全部）**：
`, ? ! : ;` 加上成对的 `( )`，**不含句号**。已做完，见下面「实际做到的范围」。

**用户原本建议记进 M8，我改记 M6——因为这个修法一个模型都不需要。**
M8 的前提是「本地模型做不了，得上云端」；全半角转换是转写后的字符替换，
落在 `TranscriptCleaner` 里即可（该文件已在做去特殊 token、剥字幕署名）。
等三个里程碑不划算。

**不能靠改 prompt 修，那条路实测会炸。** `WhisperKitTranscriber.swift:164`
记着：全角「，」是 UTF-8 三字节（EF BC 8C），用全角的 prompt 候选在 24 秒的
long.wav 上**稳定复现**同前缀字节级乱码（`Ｂ` EF BC A2、`４` EF BC 94、`�`），
换成半角后 90 次转写零乱码。Whisper 跟着 prompt 的习惯走，输出也就成了半角。

**度量看不见这件事——第三个盲区。** 基准集 23 条标准文本里 20 个逗号
**全是全角**，转写输出**全是半角**，而 `characterErrorRate` **刻意排除标点**
（「一次标点改善会掩盖一次真实的漏字」），`punctuationCount` 只数个数不分
全半角。这个不匹配从第一天就在基准集里，度量完全屏蔽了它。

因此修法要含两部分：

1. `TranscriptCleaner` 里做中文语境的全半角转换。**难点是中英混排**——
   `用 Claude Code 部署到 AWS,先跑 npm install` 里那个逗号该转全角（中文
   语境），英文短语内部的逗号该保持半角。与 `CorrectionGate.joiningLatinWords`
   处理拉丁词边界同类，有现成路子可循。
2. **给度量补一个能看见全半角的指标**，否则它会再次无声退化——
   这正是前两个盲区的教训。

**订正（独立验收 2026-08-17）：第一版指标是个恒等式，量不出任何东西。**
它最初写成 `ChineseScript.fullWidthConversions(...).count`，与转换器
**共用同一个函数**，而度量跑在转换之后——凡是该函数认得出的半角标点都
已经被它转掉了，指标必然读 0。基准集 26 条全是「半角=0」，那不是测量
结果，是恒等式。

代价是双向的：既量不出误伤（规则太激进），也量不出漏转（规则太保守）
——**规则越保守，指标越漂亮**。这是 M5「把答案抄进被测系统」那个错误的
同形缩小版。

已改为独立实现且**严格更窄**的判据（提交 `5f9524e`）：半角 `,;:?!` 两侧
紧邻都是汉字；位于文本末尾时只要求左邻是汉字（末尾那一档是最常见的真实
形态——用户日志「…把 M8 的分场景优化改成**?**」）。窄的好处是凡它报出来
的都无疑是错的，读 0 因此有意义。**它只能发现漏转，发现不了误伤**，
误伤靠钉死的测试守着。

**实际做到的范围**（`ChineseScript.fullWidthConversions`）：

| 字符 | 判据 | 改写 | 度量 |
| --- | --- | --- | --- |
| `, ? ! : ;` | 邻居规则 | ✅ | ✅ |
| `( )` | 成对规则 | ✅ | ✅ |
| `.` | 邻居规则 | ❌ | ✅ |
| `" '` | —— | ❌ | ❌ |

**邻居规则**：跳过空白**与相连的标点**后离它最近的那个实字符，两侧任一处在
「中文语境」就转全角，并吃掉紧邻的空白（换行不吃，它是内容边界）。
跨过标点是为了让 `真的吗?!`、`太好了!!!` 这种连写一起转——只看紧邻的实字符
会转出「真的吗？!」这种一半一半的结果。中文语境 =
汉字 / CJK 符号标点 `U+3000–303F` / 全角形式 `U+FF00–FFEF`；弯引号
`U+2018–201D` **不算**（英文同样在用它们）。这条同时挡住了最贵的误伤：
千分位 `1,200,000` 两侧都是数字，一个字不动；`3:30`、`16:9`、
`https://x.com/s?q=1` 同理。

**括号必须另立一条，不能照搬邻居规则。** 括号在代码、路径、函数签名里极常见
而且**成对**：`函数 foo(x) 的返回值` 里左括号前邻是拉丁、右括号后邻是汉字，
邻居规则会把这一对拆成一半一全。三条同时满足才转：

1. **成对**——配不上的一半一律不动（不成对时括号范围未知，也就无从判断
   里面是什么，而 Whisper 漏掉一半括号是常事）；
2. **括号内有中文、且没有拉丁字母**——数字放行，`（见 2.1 节）` 是正常中文
   行文，一刀切禁数字会漏掉一大类；`(large-v3-turbo)` 有字母，不转；
3. **括号外没有拉丁字母或数字粘着，且两侧至少一处是中文语境**——
   `/usr/local/bin(不要改)` 与 `render(这里传中文)` 的粘连是函数调用与路径的
   形状，中文行文里几乎不这么写（会写成「路径是 …/bin（不要改）」或至少留
   个空格），判成代码保持半角。孤零零的 `(不要改)` 外部没有中文邻居，
   多半是被截断的代码片段，也不转。

**句号刻意不改**：用户点名的是五个，句号不在其列；而且它不该顺手加进来——
`我想想...` 的三个点各自都满足邻居规则，转完是「我想想。。。」。度量照数它，
「度量该看见全部，改不改是另一个决定」。

**已知误伤，记在这里**：`写成 int x = 1; 然后编译` 里的分号会被转成全角。
这是**邻居规则本身的代价**，不是漏写的分支——它与 `部署到 AWS,先跑 npm install`
（该转）的形状一模一样，只看邻居分不开。括号靠成对判断绕开了同类问题，
`; : ? !` 没有「对」可配，绕不开。接受的理由是口述中文时说出 `;` 的场景极少，
且误伤只发生在「代码片段紧接中文」这一种排布上；真出问题时先收窄分号与冒号。
`Tests/vInputTests/PunctuationWidthTests.swift` 里有一条测试专门钉住这个行为。

**度量与转换器共用同一个函数**（`ChineseScript.fullWidthConversions`），不是
各写一遍同一条规则：括号的判据复杂得多，各写必然分叉，而分叉的两个方向都
致命——「转换器改了但度量看不见」，以及「度量把转换器刻意不改的代码括号记成
退化」（指标从此恒不为零，没人会再看它）。

### M5 独立验收结转的两条

- **补技术类留出样本**（来自 M5 验收 B1）：基准集的技术术语被逐字写进了
  生产 prompt，`BenchMetrics.technicalTerms` 又是从参考文本抽词，于是

## M7 蓝牙鼠标接入

用户新购一支带收音功能的蓝牙鼠标（系统里叫 **`iMouse`**，Freqchip 芯片），
作为第三个音频源。

**架构上早留好了位置**：M3 把遥控器与内置麦的全部差异吸收在 `AudioSource`
protocol 之后，上面各层不知道音频从哪来。`AudioSourceRouter` 已支持多源路由。

### 侦察结论（2026-08-18 真机实测，三步走完）

动手前那条「先看系统设置的『声音 → 输入』里有没有它」已经查过，**没有**。
原因是它只有 BLE、没有 HFP/A2DP（`Services: 0x400000 < BLE >`），
因此不可能注册成系统音频输入设备。形态与 RC003 相同：BLE + HID。

**我当时写的两条判断都是错的**，记在这里免得重犯：

- 「音频必然走自定义 GATT」——过度推断。`0x400000 < BLE >` 只说明它是 BLE
  设备，说不了 GATT 还是 HID-over-GATT。（实测确实走 GATT，但那是运气。）
- 「不讲 ATVV 就等于重做一遍 M3」——高估。实测协议比 ATVV 简单得多。

**扫描器差点白做一轮**：macOS **不把 HID over GATT（服务 0x1812）交给
CoreBluetooth**，纯 GATT 扫描在这类设备上可能打出近乎空的服务列表。
实现方自行加了 HID 探针并排跑，理由是「两条路一起看的成本是一个文件，
白按一轮的成本是把用户叫回电脑前重来」——这个判断是对的。
另一个坑：**系统已连接的 BLE 设备不广播**，必须先
`retrieveConnectedPeripherals(withServices:)`，`scanForPeripherals` 永远扫不到。

#### GATT 结构

```
180A 设备信息   厂商 = "Freqchip"   固件 = "0122"
FFF1            ← 语音通道
  0783B03E-8535-B5A0-7140-A304D2495CB8   writeWithoutResponse,write,notify
  0783B03E-8535-B5A0-7140-A304D2495CBA   notify
02F00000-…-FE00 OTA 服务
180F 电池
```

**控制帧与音频复用 `…CB8` 这一个特征**（它可写可通知）。

#### 会话协议

控制帧 17 字节：`0A 77 FF 34 1B <码> 0A 06 07 09 <MAC 6 字节> 44`

| 码 | 含义 |
|---|---|
| `0x51` | 语音键按下（唤醒/准备） |
| `0x21` / `0x22` | 语音键 开始 / 结束 |
| `0x23` / `0x24` | 另一个键 开始 / 结束 |
| `0x27` / `0x28` | 第三个键 开始 / 结束 |
| **`0x31`** | **长按开麦，见下方警告** |

规律是**奇数开始、偶数结束**。其他按键也会短暂开麦（零点几秒），
大概是鼠标上的其他 AI 功能键。

#### ⚠️ `0x31` 没有配对的结束码，会无限期送流

2026-08-18 实测触发过一次：**鼠标持续送流 11 分钟**，把用户不知情的房间
环境音送了过来并被写进抓包日志（已删除）。用户是靠菜单栏的麦克风图标
才发现的。

**M7 的实现必须处理这一档**：要么主动发停止命令，要么设上限自己断开。
M3 的 `VoiceSessionKeepalive` 有 180 秒上限，这里需要方向相反的同类机制
（防止不停，而不是防止被切断）。

**同类的教训更普遍**：任何诊断工具在长时间无预期地接收数据时，都该自己
停下来并告警，而不是闷头记录。`scripts/mouse-decode.sh` 已加时长上限
（提交 `b7ca232`）；**BLE 扫描器本身还没有**，是一条待办。

#### 编解码：标准 SBC，不是 ADPCM

**我猜「高度疑似 IMA ADPCM」是错的，而且是最危险的那种错——理由听起来
完全成立。** 静音段大量 `55 55 75` 确实像 IMA 中间码字。实测四种组合
（帧头 3/4 字节 × 高/低半字节在前）：样本 55–62% 撞满量程、直流偏置顶到
+18000。原因很直白：**IMA 的符号位是 nibble 的 bit3，`5/6/7` 全是正号**，
重复它们不是静音，是 predictor 恒定爬升。

真相：`9C 31 0C xx` 是 **A2DP 的 SBC frame_header**，逐位对得上——

| 字节 | 含义 | 值 |
|---|---|---|
| `9C` | syncword | SBC 固定（mSBC 是 `0xAD`）|
| `31` | 配置 | **16 kHz / 16 blocks / MONO / Loudness / 8 子带** |
| `0C` | bitpool | 12 |
| `xx` | **CRC-8** | poly 0x1D、init 0x0F |

**CRC-8 在 7872 帧里 7872 帧命中——这是判定，不是「像」。**
帧长 `4 + 4×8×1/8 + ceil(16×1×12/8) = 32` 字节，每帧 128 样本 = 8 ms，
每包 4 帧 = 32 ms，与实测包间隔（31.25 包/秒）吻合。
采样率两路互证：帧头写 16 kHz，481 秒长基线反算 15993 Hz（误差 0.04%）。

**「8 kHz 最可能」也是我猜错的**——按 4-bit ADPCM 估的压缩比，
而 SBC bitpool=12 省一半。

#### Swift SBC 解码器（已完成，提交 `71d0e66`）

`Sources/vInput/Audio/Vendored/SBCDecoder.swift`，从 **FFmpeg n8.1** 的
`sbcdec_data.h` / `sbcdec.c` / `sbc.c` 移植（LGPL-2.1+ → 可并入本仓库的
GPL-3.0，文件头写明出处与适配）。选 n8.1 是因为本机 ffmpeg 是 8.1.1，
**参考答案就是这个二进制解出来的，版本对不上等于换了标尺**。

**验收判据是零容差逐样本吻合**：298496 个样本、5 段真实录音，与 ffmpeg
输出 **0 个不同**。不设阈值是因为不需要——定点实现的直译在补码下位模式
等价，**任何非零误差都意味着抄错了**。实测：proto filter 表改错一位，
最大误差恰好是 1；若允许「误差 ≤ 1」，这个错就藏进去了。

**判据本身也被验了。** 实现方做了 12 处人为改动（六张系数表各改一个数、
两张 offset 表各改一行、反量化的 `+1`、CRC 初值、m0/m1 对调、
`EXTRA_BITS` 2→1），确认每一处都被抓到。**其中一处最初没被抓到**：
Loudness 的 offset 表按「采样率 × 子带数」索引，而夹具只走到 16 kHz 那行，
改错 32/44.1/48 kHz 的行测试照样全绿——补齐夹具后才抓到。
**「全绿」不等于「抄对了」，只等于「测试没抓到错」。**

拒绝的配置（帧头逐字段校验，没有一项是假设）：立体声各档、mSBC
（syncword `0xAD`）、坏 syncword、bitpool 越界、CRC 不符、头部截断。
**声道模式的检查放在 CRC 之前**（上游是之后）：配置位一变 CRC 必然也对
不上，先报 CRC 错会让日志说「码流损坏」而真相是「固件换成立体声了」。

##### 交互保持「按住说话」，不做 toggle（2026-08-18 用户决定）

用户提过改成 toggle：按一下鼠标语音键 = 按下 ⌥D，再按一下 = 再按一次。
理由很对——**鼠标不是遥控器，按住不放不舒服**。

**但硬件不允许**：鼠标只在按住时送音频（`0x21` 开始 → 音频 → `0x22` 结束，
而 `0x22` 是松手时发的）。短按一下只有约 0.2 秒——实测其他按键的
`0x23` / `0x27` 会话分别只有 0.35 秒和 0.09 秒。这是固件行为，改不了。

因此 toggle 语义下**音频只能来自内置麦克风**，鼠标退化成一个按钮，
它自己的麦克风用不上——而那正是买它的理由。**用户据此决定不改。**

唯一可能同时拿到「toggle + 鼠标麦克风」的路是 `0x31` 长按持续模式，
但**不知道怎么关它**（实测开了 11 分钟无结束码）。要走这条路得先摸清
停止方式，需要真机试探，是另一轮的事。

##### `0x31` 的保护：两档上限

| 会话类型 | 上限 | 撞线后 |
|---|---|---|
| 语音键（`0x21` → `0x22`） | **90 秒** | 收尾转写已录到的部分，再退订 |
| `0x31` / 未知奇数码 | **30 秒** | 直接退订，**不产出任何文本** |

两类会话的代价不对称：前者是用户按着键在说话，撞线只是少了后半句；
后者没有人在等它结束，多开一秒就是多收一秒没人想录的音频。

90 秒的依据：RC003 固件 60 秒切断，实测支撑「手按着说话不会超过一分钟」；
`scripts/mouse-decode.sh` 的离线路径已用 90 秒（`b7ca232`），同一支设备同
一个数，日志与脚本对得上。**不照搬 `VoiceSessionKeepalive` 的 180 秒**——
那边固件自己 60 秒就断，应用侧是第二道兜底；这边 `0x31` 没有任何硬件兜底，
我们这道是唯一的一道。30 秒对 `0x31`：把最坏情况从 11 分钟压到 30 秒。

撞线后退订并冷却（10 秒起，连续撞线翻倍，封顶 300 秒），恢复订阅后**必须
有新的开始码**才再接收音频——否则设备若还在那条陈旧的流上，恢复等于立刻
再收一遍。**不发写入命令去关麦**：`…CB8` 可写，但没有已知的停止命令字节，
为了试它去猜可能让设备进入未知状态，收益只是省掉一次退订。

`0x23` / `0x27` / `0x31` 一律不启动听写，只计时并在撞线时退订——前两个是
别的 AI 功能键（实测只开麦零点几秒），转写它们只会产出垃圾；`0x31` 更不该
把一段没人想录的音频注入到前台应用里。

##### 两个协议判断，都有抓包证据

- `0x51` 不当开始码：3/3 次 `0x51` 之后 0.31 秒必跟 `0x21`，两者之间
  **一个音频包都没有**（`capture.log` 第 542 行到第 556 行）。按「奇数即
  开始」处理会让每次按键多开一个空会话。
- 帧内那 6 字节地址**只记录不校验**：抓包里是 `C9 00 …`，系统蓝牙面板显示
  `C9:01:…`，第二字节对不上。没查清之前拿它当判据等于埋一个「换支鼠标就
  全不认识」的坑。

##### 按键抓取：走了「会话期间无条件抑制」

**usage / 键码没抓到**（上一轮扫描的 HID 报文只按 report ID 汇总了），
等用户再按一轮键来定这个数会把整个里程碑卡在一次真机往返上。
`RemoteKeySuppressor` 因此加了两档策略：RC003 仍是 `.only([F5])`（实测），
鼠标是 `.allExcept([Esc])`。

取舍不对称：漏抑制的后果是输入框被按键垃圾填满、注入的文字被淹没
（M3 在 RC003 上实测过的现象）；多抑制的后果只是说话那几秒键盘不响应。
`Esc` 必须留——它是录音期间唯一的取消键。鼠标按键本身不是键盘事件
（tap 只挂 `keyDown`/`keyUp`），点击与滚轮全程不受影响。

**这是本轮唯一的已知缺口。** 会话期间每个按下沿仍记日志，键码就靠它实测
出来；拿到之后应当把鼠标也收窄成 `.only(...)`。

##### 两条旧待办一并了结

- **BLE 扫描器的自我保护**已加：单段连续流超过 90 秒（空档 2 秒即分段）
  自动退订并停止扫描，判在落盘之前——一旦决定停，这一个包就不该再写进
  文件。正常用法（按几秒、松开、再按几秒）不会误伤。
  **后来补了第二道**（独立验收指出）：只有单段上限时，「89 秒 + 松 3 秒 +
  89 秒 + …」可以无限累积落盘而守卫一声不吭。现在再加一道 180 秒的总量
  上限，两道各管一种形状。同时把告警文案改对——原文案「这段音频不再落盘」
  只对触发的那一个包成立，之前的约 2800 个包早就在盘上了。
- **双设备共存**已堵：两座桥互相排除对方当前占着的 identifier
  （`AppModel.startRemote` / `startMouse`）。

##### 一条新的失效链（三个源之后才出现）

鼠标正录着（按键抑制归它的会话），用户按遥控器语音键 → 被守卫拒 →
若走 `handleVoiceStop()` 去清状态，遥控器的 `onFinishSession` 会调
`endSuppressing()`，把鼠标那次的抑制一起关掉。两个协调器因此各加一个
`abandonSession()`：清状态但一个回调都不发。守卫本身也从两条变三条
（加 `dictationIdle`）并改名 `voiceDeviceStartAllowed`。

## ⚠️ 两处生产代码崩溃（2026-08-18 发现，未修，优先级高于任何新功能）

M8 Task 5 的实施者在跑测试时发现 `./scripts/test.sh` **约 2/8 次崩溃**。
它一度怀疑是自己引入的，查了崩溃报告——**不是**：同样的签名在
2026-08-11 与 2026-08-18 的 17:01 / 17:42 / 17:43 / 18:14 / 18:16
就已存在。基线连跑 5 次干净只是运气。

`~/Library/Logs/DiagnosticReports/` 下 7 份 `.ips` 佐证。**两条签名都在
生产代码里，不是测试脚手架。**

### ① `RemoteKeySuppressor.handle` 野指针（SIGSEGV，5 次）

```
__CFMachPortPerform → eventTapMessageHandler → _XPostEventTapData
  → processEventTapData
  → @objc closure #1 in RemoteKeySuppressor.start()
  → MainActor.assumeIsolated
  → RemoteKeySuppressor.handle(type:event:)
  → shouldSuppress(keyCode:) → Policy.suppresses(keyCode:)
  → Set.contains  →  SIGSEGV / swift_retain 捡到野指针
```

两次的地址形态不同（一次 `0x0f3737b33f3737b8`，报「possible pointer
authentication failure」；一次 `0x0000000d8c9b3468`），**都是读到了不该读
的内存**，典型的释放后使用或跨线程撕裂。

**两个候选成因，没定论，要查：**

1. **`MainActor.assumeIsolated` 在 tap 回调里是断言不是切换。** 它不把执行
   搬到主线程，只是声称「我已经在主线程」。若 tap 装在非主线程的 run loop
   上，这句话是假的，随后触碰 MainActor 隔离的 `policy`（那个 `Set`）就是
   跨线程数据竞争。**release 构建里这个断言根本不检查。**
2. **对象析构了而 tap 还挂着。** 回调持有的 `self` 若是裸指针/`Unmanaged`，
   析构后回调再触发就是释放后使用。

**为什么在测试里最容易撞上**：测试会**真的装一个 CGEvent tap**。
本会话早先已经发现同类问题——`swift test` 曾真的往前台应用注入 Return 键
（默认 `SystemKeyPoster()`，没有替身）。当时 QA 的原话是「至今没造成伤害
多半只是因为跑测试的进程没有辅助功能授权——那是运气不是设计」。
**这两件事是同一个根：测试里跑了真的系统副作用。**

**真机风险**：同一段代码在 app 里跑，遥控器/鼠标语音会话期间挂 tap。
崩了就是整个 app 挂掉，正在说的那句话全丢。

### ② `SBCDecoder.calculateBits` **死循环**（2026-08-19 抓到实证，诊断已更新）

**先前记的是「数组越界，间歇发生，疑似并发共享状态」——不准确。**
2026-08-19 在本机抓到一个跑飞的测试进程，`sample` 出来的证据：

```
swiftpm-testing-helper --filter SBCDecoder   98.2% CPU   1400 分钟 CPU 时间
Call graph（1405 个采样）：
  SBCDecoderTests.matchesFFmpeg(fixture:)
    → SBCDecoder.decode<A>(_:)
      → SBCDecoder.decodeFrame(_:at:info:into:)
        → static SBCDecoder.calculateBits(info:scaleFactor:)   ← 1075 / 1405 个采样
```

**它不是崩了，是死循环了 23 小时**，一直占着一整个核。

**新诊断**：位分配（bit allocation）那个循环在某些输入上**不收敛**。
越界与挂死**是同一个根因的两种表现**——循环跑飞后索引一路增长，
撞上边界检查就是 SIGTRAP，没撞上就一直转。

这也解释了「固定 fixture 却间歇崩」：不是并发共享状态，是**同一个不收敛
的循环，每次跑飞到哪一步取决于调度**。

**真机风险比原先估计的更高**：死循环不会像崩溃那样留下报告，
表现是**鼠标收音时整个 app 卡住、风扇转起来**。
**用户此前报过「无法使用鼠标收音」，当时没查出原因——这条现在是首要嫌疑。**

**怎么查**：`calculateBits` 是从 FFmpeg n8.1 移植的（`Audio/Vendored/SBCDecoder.swift`，
535 行）。对着 FFmpeg 原版逐行比对那个循环的**终止条件**——移植时最容易
丢的就是它。上游用 `bitcount`/`bitslice` 做收敛，任一个比较写反或者
初值取错都会让它永不退出。**先给循环加一个硬上界让它可复现地失败**，
再去找真正的差异。

### ②-旧 `SBCDecoder.decodeFrame` 数组越界（SIGTRAP，2 次）

```
SBCDecoderTests.matchesFFmpeg(fixture:)
  → SBCDecoder.decode<A>(_:)
  → SBCDecoder.decodeFrame(_:at:info:into:)
  → Array.subscript.getter → _checkSubscript → 越界陷阱
```

**输入是确定性的（固定 fixture），却间歇崩**——这本身就是线索：
同一份输入每次结果该一样。指向**并发测试之间共享了可变状态**
（Swift Testing 默认并行跑），或者解码器内部有跨调用残留的状态。

**真机风险**：这是鼠标收音的解码路径（M7 从 FFmpeg n8.1 移植的 535 行）。
越界在 app 里就是崩溃。**用户此前报过一次「无法使用鼠标收音」，
当时没查出原因——不能排除是同一件事。**

### 怎么查

**不要在 M8 分支上修**，另开分支/worktree。建议顺序：

1. 先让崩溃**可复现**：`./scripts/test.sh` 连跑 20 次统计频次，
   分别单跑 `--filter RemoteKeySuppressor` 与 `--filter SBCDecoder`
   看两条签名是否独立出现。
2. `RemoteKeySuppressor`：查 tap 装在哪个 run loop、回调怎么持有 `self`、
   `stop()` 有没有在析构前一定被调到。**顺带把「测试里装真 tap」这件事
   一起解决**——它和「测试里注入真按键」是同一类问题。
3. `SBCDecoder`：`.serialized` 跑一遍看还崩不崩，能定位是并发还是逻辑。

**这两条的优先级高于任何新功能。** M6 那一轮的主题就是「说过的话不再
无声消失」，而这是「说到一半整个 app 没了」。

## 翻译把中文大数译错了（2026-08-19 实测发现，未修）

**长文本实测里抓到的，与长短无关，但与报价场景直接相关。**

同一段话里：

| 原文 | 译文 | 对不对 |
|---|---|---|
| 七十亿参数 | "7-billion-parameter" | ✅ |
| **四十亿参数** | **"40-billion-parameter"** | ❌ **差十倍** |

四十亿 = 4 billion，模型给的是 40 billion。同一个模型、同一段话、
相邻两句，一句对一句错——**说明这不是「不会」，是不稳**。

### 为什么现有的度量看不见它

`TranslationMetrics.digitsIn` 只统计 **ASCII 数字**（这是 2026-08-19 修过
一次的判据：原来用 `Character.isNumber`，而 Swift 的 `isNumber` 对「三」
「百」「十」全返回 true，造出过 100% 假阳性）。

而「四十亿」里一个 ASCII 数字都没有。**这一类错误目前完全不在度量的
射程内**，长文本那一轮的报告里「数字丢失」显示的是「分母为 0，读不出
任何东西」——报告说得没错，但它不知道自己漏了什么。

### 为什么它比看上去要紧

用户说过：这个工具未来会涉及**报价**，而数字译错是报价场景里最贵的错。
中文口语里说金额、数量几乎全用「万」「亿」——「一百二十八万」
「三千五百万」——**恰恰是这一类**。而阿拉伯数字那批已经实测过 12 条，
一个都没错（`Bench/translate-digits.json`）。**风险全集中在没测的这半边。**

### 怎么查

1. **先补素材**：一份中文数词语料（万 / 亿 / 千 / 百，配金额、数量、
   人数、百分比），量一量错误率有多高——现在只有一个样本，
   不知道是万分之一还是十分之一。
2. **再补度量**：要能把「四十亿」与 `4 billion` / `4,000,000,000` /
   `four billion` 对上。这比 ASCII 数字比对难，但没有它就永远只能靠肉眼。
3. **可能的修法**：在提示词里单列一条中文数词的规则（现有三条规则里
   「保留所有数字」对中文数词是无效的——它字面上就只说了 numbers）。
   **改完必须用第 1 步的语料复测**，否则又是一次「看着在改其实没改」。

**优先级**：高于任何新功能，低于那两处崩溃。报价场景是这个产品的立身之本，
而这一类错误**用户自己看不出来**——译文流利、格式正确、只有数量级是错的。

## 输入设备收尾（新增，2026-08-18 记，未排期）

几个悬着的设备级问题攒到一起做。**攒着的理由是真机往返是这个项目最贵的
资源**——每问一次用户按键、重启、复现，都要占掉他一段时间，M7 期间为此
卡过好几轮。一次真机会话把下面几条一起测掉，比分三次划算。

### ① 遥控器关机键改成退格键（2026-08-18 用户提出）

**现象**：小米遥控器（RC003）上的关机键误碰后**直接关掉电脑屏幕**。
用户希望把它当退格键（Delete / Backspace）用。

**难的不是「发退格」，是「拦住关屏」。** 注入退格用现成的 `KeyPoster`
一行就够；真正的问题是那次按键**已经被系统消费掉了**，我们要抢在前面。

**先做侦察，30 分钟，决定后面值不值得做：**

1. 按一下关机键，看 `RemoteHIDListener` 的 usage 日志里**有没有它**。
   `HIDReportParser` 里那张 2026-08-15 的实测按键表（`0x28` 确认 /
   `0x3E` 语音 / `0x4F–0x52` 方向 / `0xF1` 返回）**没有关机键**——
   要么当时没按到，要么它压根不走 report ID 1。这一条决定后面全部路径。
2. 如果日志里有，就能识别；**但识别不等于能拦**，屏幕照样会关。

**已知的技术障碍（写下来免得下一轮重新推一遍）：**

- 关机／睡眠键大概率走 **Consumer Page usage `0x30`（Power）** 或
  Keyboard Page `0x66`，macOS 对这一档有特殊处理。
- 现有的 `RemoteKeySuppressor` 挂的是 CGEvent tap 的 **`keyDown`/`keyUp`**。
  电源与媒体键到达时是 **`NSSystemDefined`（type 14）事件，不是 keyDown**
  ——**现有的 tap 根本看不见它**。要试就得把 `.systemDefined` 加进事件掩码。
- 媒体键（播放/音量）用 systemDefined tap 拦截是成熟做法，所以有戏；
  但电源键是不是也放行，**没验过，不要当成已知**。
- 最后的手段是 `kIOHIDOptionsTypeSeizeDevice` 独占设备，**但那会连方向键
  和确认键一起吞掉**（那两个现在靠系统原生投递，见按键表），等于把 M3
  已经能用的东西弄坏。**代价不对称，不要走这条**，除非前面全不通。

**做不成也是一个合格结论。** 那时的答复是「macOS 不放行电源键」，
比含糊地拖着强。

### ② 鼠标第三键的抑制是否必要（M7 结转）

日志里**一条 `keyCode` 都没有**，说明鼠标那个键可能压根不产生键盘事件，
`RemoteKeySuppressor` 对鼠标用的 `.allExcept(...)` 宽策略也许整个是多余的。
多抑制的代价是说话那几秒键盘不响应——不大，但也不该白付。
**同一次真机会话顺手验掉。**

### ③ 鼠标控制帧 `0x31` 的触发动作未知（M7 结转）

已排除「语音键长按」。现在按未配对起始帧处理并加了 3 秒宽限保护。
**知道它是什么按出来的，才能确认那层保护拦的是对的东西。**

### 排期建议

**排在 M8 之后、M9 之前，不要插进 M8。** M8 是翻译，正在跑，和这些
一点关系没有；而这三条都要真机、都不阻塞任何人，攒一批做正合适。

## M8 场景风格、润色与多语种输出

三个 profile（技术 / 口语 / 书面）按前台应用的 bundle ID 切换，
完整标点、分段、去口水词。

### 大原则（2026-08-17 用户确立）：一切不出本机

**理由是用户给的：未来会用它口述机密内容，包括报价。**

这条**收紧**了原始设计的「音频不落盘」——现在是内容本身也不出本机，
不只是音频文件。它与同日选定 Gemini 的决定**直接冲突**，M8 设计时必须
正面处理，不能两条都记着当没看见。

**冲突比表面更尖锐**：最需要翻译的场景与最机密的内容是同一批。要把报价
发给国外客户，那句话既是要翻译的、也是不能出机的。「本地转写 + 云端翻译」
这个分工恰好把最敏感的内容挑出来送了出去。

按目标语言分，可行性完全不同：

| | 本地可行性 |
|---|---|
| 中 → 英 | **可以**。WhisperKit 的 `task: .translate` 由 Whisper 自己完成，纯本机，一个参数的距离 |
| 中 → 西 | Whisper 做不到。只能本地 LLM（未测量）或云端 |
| 场景润色 | 本地 4B 已实测吃力；8B / 14B **未测量** |

用户的直觉「多语言不出本机可能性不大」**对西语成立，对英语不成立**。

因此 M8 应当先穷尽本地路径再谈云端：先试 Whisper 原生 translate（中→英），
再用基准集测本地 8B/14B 能否胜任西语与润色。**云端是兜底，不是默认。**
若最终仍需云端，它必须是显式的、每次可见的、可关闭的——而不是某个 profile
自动触发。

**2026-08-17 扩大范围：把「翻译成其他语言」并入 M8。**

用户提出想把中文语音输出成英语 / 西语文字。现状核实：**完全不支持**，
代码从未设置 `DecodingOptions.task`，走默认的 `.transcribe`。

分两种情形，差别很大：

- **中文 → 英语**：WhisperKit 有 `task: .translate`，技术上就是改一个参数。
  但 `punctuationPrompt` 是中文的、`normalizeToSimplified` 与
  `TranscriptCleaner` 都按中文输出写、拼音闸门对英文无意义、
  **基准集全是中文参考文本因此零度量能力**。
- **中文 → 西语**：**Whisper 做不到。** WhisperKit 自己的注释写死了
  （`Configurations.swift:135`）：`translate` 是 X→**English**，
  没有其他目标语言。这是模型能力边界，不是参数问题。

因此翻译与润色是同一类操作——都要重写文本、都过不了拼音闸门、
都需要更强的模型。**应当共用同一套安全网，并入 M8 一起设计。**

### 云端默认关、用户显式开（2026-08-18 用户决定）

用户澄清了「一切不出本机」的边界，**这条比原先记的更准确**：

- **产品原则**（为将来的用户）：尽可能一切留在本地。
- **开发期约束**（作者自己的机器）：**不存在**。用户原话：「我自己的信息
  上传到云端没问题，因为我不涉及到任何的保障安全的内容。这个工具未来给
  其他人用，可能会涉及。」

所以 `MouseDecode/`、`Bench/audio/`、抓包日志落在 OneDrive 同步目录里
**不是问题**，不必加警告、不必改 `.gitignore`。而 8-18 那次「11 分钟环境音」
事故的严重性也要重新归类：**它不是隐私问题，是两件别的事**——麦克风在用户
不知情时开了 11 分钟（可靠性），以及日志说「已停止」而实际没停（排查时会
被误导）。两条都仍值得修，但**理由变了，将来的取舍也会跟着变**。

因此 M8 的云端不是「要不要做」，是**默认关、用户显式开**。

### 默认翻译后端待定：Qwen 7B vs Whisper 的 translate（未对照）

**记录一处我说错过的事实**：2026-08-17 那次翻译实测用的是本地
`qwen2.5-7b-instruct-4bit`（MLX），**不是 Whisper Turbo**。

| | 测过没有 | 结果 |
|---|---|---|
| Qwen2.5-7B 中→英 | ✅ | 三条全可用，1.7–3.3 秒 |
| Qwen2.5-7B 中→西 | ✅ | 三条里两条不能用 |
| **Whisper 的 `task: .translate`** | ❌ **完全没测** | 只知道它存在，且**只能译成英语** |

Whisper 的 translate 是模型内置能力，把音频直接译成英文、不经过中文文本，
是完全不同的路径。**M8 开工时先用基准集音频跑一轮对照，再定默认值。**

### 「本地零出站」要做成可验证的属性，而不是一个设置

设置可以被绕过、被误配，也无法向别人证明。而「本地模式下应用不发起任何
出站连接」是能验证的——抓包就完了，也能写进测试。

容易漏掉的出站：模型下载（`WhisperKitTranscriber` 的 `modelName` 默认值
`"base"` 就会联网拉）、崩溃上报、更新检查。

**不写「符合 GDPR」这种法律结论**；「个人数据不离开设备」是可验证的事实，
而它恰好是 GDPR 下最省事的姿态——数据不出去，大部分义务不适用。

### 后端选型：Codex CLI 实测不可行

用户提议复用本机已装的 `codex` CLI（0.145.0，有非交互的 `codex exec`），
省掉 API key 管理。**实测否决**（2026-08-17，翻译一句 46 字中文）：

| 配置 | 耗时 | 结果 |
|---|---|---|
| 默认（`reasoning effort: high`） | **39.8 秒** | 译文正确，用掉 6,608 token |
| `model_reasoning_effort=minimal` | **29.7 秒** | 失败（exit 1，无输出，未深究） |

译文质量确实好（「scenario-specific optimizations」这种译法本地 4B 给不出）。
**问题不在质量，在形状**：

- **约 30 秒是固定开销的地板**，不是推理慢——启进程、装 skills、刷模型列表
  （首次跑还超时报错）、跑 agent 循环。降到最低推理档一秒没省下来。
- **一句话 6,608 token**，绝大部分是 agent 脚手架，等于每次听写都啃掉
  用户 Codex 额度的一大块。
- 它是带沙箱和工具调用的 **agent 循环**，我们要的是一次文本补全。
- 0.145.0 版本号仍在快速变动，输出格式不是稳定接口。

**改为直接调 API**，一次 HTTPS POST，一段话约 1–3 秒，key 放 Keychain。
后端应做成可插拔，让「换更强的本地模型」这条路留着——用户
「本地肯定做不成」是合理推测但未经测量，而 M5 之后我们有能力测量它。

**2026-08-17：用户选定 Gemini。** 翻译是它的强项，免费额度对个人用量够用。

注意 Gemini 的 API 形状与 Anthropic / OpenAI 的 messages 接口不同
（`generateContent`、`contents`/`parts` 结构），可插拔后端的接口设计要能容纳
这个差异，不能照着 messages 接口的形状硬套。

### API key 的存放：不进对话、不进仓库

**key 由用户自己放进 Keychain，任何时候都不要贴进对话。** 对话记录以明文
长期留在 `~/.claude/projects/…/*.jsonl`；本仓库又在 OneDrive 下，提交即上云。
两条都是不该放密钥的地方。

M8 开工时由用户在终端执行（`-w` 后不带值，交互式输入，key 也不进 shell 历史）：

```
security add-generic-password -a vInput -s vinput-gemini-api-key -w
```

应用启动时从 Keychain 读，读不到就禁用云端后端并在 HUD 提示——**不要**
回退到「静默不工作」，那是 M6 ③ 正在修的同一类问题。

### 两个必须先解决的设计问题

**1. 没有闸门时靠什么保证不改变原意？**

M4 的安全网是拼音闸门——同音才准改，机器可验证。**润色天然要改读音**
（加标点、去口水词、改书面语），闸门完全用不上。

这个风险 M4 期间实测发生过：模型建议过 `小米→米粒`、`情况→状况`；
某一版提示词让 `小米遥控器→小米耀空气` **真的被应用了**（同音，闸门放行）。
没有闸门，这些会直接落到用户的文字里。

**2. 本地模型做不做得了？**

用户提出的判断：Qwen3-4B 连「只改同音错字」这个更简单的任务都吃力
（六段测试修对 1 次），而润色是带风格约束的语义改写，难度高一个量级。
**能力更弱的模型配更弱的安全网**，是个危险组合。

应当重新评估原始设计里那条「可插拔，默认本地，云端可选」——M4 选了只做
本地，对校正是对的（有闸门兜着），对润色可能不成立。

**换成云端强模型能提高「改得对」的概率，但不提供任何验证手段。**
M4 期间 `小米遥控器 → 小米耀空气` 是闸门放行的漏网之鱼；M8 连闸门都没有。
用更强的模型是把风险降低，不是消除——**这是 M8 brainstorming 的核心议题，
模型选型反而次要**。

**3. 隐私：这是产品性质的改变，需要一个明确决定**

原始设计是本地优先（「音频不落盘」是写进 spec 的原则）。把用户说的每句话
发到云端 API 与此冲突。这个决定应当被明确做出并写下理由，不能顺势滑过去。

**2026-08-17 用户选定 Gemini，等于对这条做出了决定：M8 的润色/翻译路径上，
用户的语音内容会发送给 Google。** 记在这里，是为了让它是一个被明确做出的
决定，而不是「因为选了某个 API 所以顺带发生了」。

仍需在 M8 设计时明确的：走云端的是**转写后的文本**还是音频（应为文本，
音频不出本机这条原则不必因此放弃）；是否保留一个「本次不走云端」的开关；
以及走了云端时 HUD 是否要有可见标识。

**4. 交互：翻译/润色是每次听写都做，还是显式模式？**

直接决定延迟预算。校正层是 8 秒（M4 实测定的）；若做成显式模式
（另一个快捷键，或遥控器的另一个键——`0x4F–0x52` 方向键与 `0xF1` 返回键
在 M3 期间都已抓到 HID usage 且当前无用途），预算可以宽松得多。

## Windows 版（暂不排期，2026-08-18 记）

用户：「如果想让更多的人使用，Windows 的版本我们肯定是要提供的。但确实
可以放到后面再说。」

**大模型是最容易换的那一层，不是最难的。** 实际卡住的是别的：

| 层 | Mac | Windows |
|---|---|---|
| 转写 | WhisperKit（Core ML） | 整个换掉：whisper.cpp / ONNX |
| 文字注入 | `CGEvent` | Win32 `SendInput` |
| 蓝牙 | CoreBluetooth | WinRT BLE |
| 全局快捷键 | Carbon `HIToolbox` | `RegisterHotKey` |
| 音频采集 | AVAudioEngine | WASAPI |
| 界面 | SwiftUI + AppKit | 全部重写 |
| **本地大模型** | MLX | llama.cpp —— **这层反而最好换** |

**好消息：42/69 个源文件只依赖 Foundation**，而且恰好是最值钱的那些
（校正闸门、拼音、prompt、标点规则、度量、鼠标协议、SBC 解码器、
会话状态机、`AudioSource` 抽象）。剩下 27 个是平台外壳。

**这不是规划出来的，是被 TCC 逼出来的**：测试进程拿不到麦克风、辅助功能、
蓝牙权限，所以每次想测什么就得把判断从系统调用里抽出来
（`benchToggleAction`、`remoteStartAllowed`、`KeyPoster`、
`MouseVoiceSession` 与桥分离、`SBCDecoder` 纯整数运算）。
**为了可测而做的拆分，顺带买到了可移植。**

**现在该守住的只有一条**：M8 的润色层保持在纯 Foundation 那一半——
后端抽成协议，prompt / 安全网 / 场景判定不碰系统 API，只有「怎么调
Gemini」「怎么调 MLX」那层允许平台相关。照 M4 的
`CorrectionPipeline`（纯）/ `Corrector` 协议 / `MLXCorrector`（脏）
那个结构即可，不用额外设计。

Windows 上跑本地大模型的可行性差异极大——带独显的往往比 M3 Air 还快，
普通办公本每秒几个 token。**这个方差本身就是产品问题**：没法对用户说
「本地模型可以用」，因为对一半人是真的，对另一半是假的。

## M9 分发准备

从 M6 推迟过来的、「准备给别人用」才需要的：

- 设置界面（profile 编辑、模型选择、各项开关的统一入口）
- 权限引导 / onboarding（首次启动引导授权与模型下载）
- 长文本剪贴板路径的实际验证（`RoutingTextSink` 有 100 字阈值，未验证过
  长文本的真实表现）

**推迟的理由**：产品目前只有作者一个用户。这些需求等真要分发时会更清楚，
现在做容易做出一个届时要推翻的东西——与 M4 把润色推迟到有场景之后是
同一个判断。
