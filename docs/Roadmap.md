## 与原始设计的差异及理由

**原 M4「润色层」收窄为「校正层」，润色并入后续。**
润色的正确答案依赖场景——同一句话在 Cursor 里该保留术语原文，在微信里该保留
口语感。脱离场景做，会做出一个后续必须推翻的东西。

**原 M5「场景风格」顺延，M5 改做转写质量。**
M4 收尾的真机数据：六段标准测试**七个错误只有一个是下游能修的**，其余全是
转写层的漏字、听错、大小写；而下游看不到音频，声学证据已经没了。在转写层
不够好的时候做润色，等于在一段已经错了的文字上精修排版。

**M7 蓝牙鼠标插在 M6 与润色之间**（2026-08-16 决定）。

## M6 稳固化（精简版）

**2026-08-17 决定：M6 只做可靠性，分发相关的功能推到 M9。**

理由：产品目前只有一个用户（作者本人）且已在日常使用。设置界面、onboarding
这类是「准备给别人用」才需要的，而「用着用着话就没了」是每天都在发生的。
先把可靠性做到位，分发的需求等真要分发时也会更清楚。

### 四项（按现状核实过，不是照抄原设计）

**⓪ 超过约 30 秒的语音被静默截断（2026-08-17 用户报告，日志已确认）**

**这是主路径上的静默丢字，优先级高于下面四项。**

真机证据，session 103：

```
16:03:17.983  遥控器语音键按下，开始录音
16:03:27.926  ATVV MIC_EXTEND request      ← 三次续期
16:03:37.926  ATVV MIC_EXTEND request
16:03:47.926  ATVV MIC_EXTEND request
16:03:49.421  遥控器语音键松开，进入转写
16:03:59.679  本次能量：304 个块 超阈值 145 个 (47%)
16:03:59.679  注入成功 文本(81字): …我在想,有没有可能把 M8 的分场景优化改成?
```

**31.4 秒只出 81 字，且断在半句上**——「改成**?**」后面没了。按用户基准集
实测语速 3.1–4.6 字/秒，31.4 秒应有 100–140 字，**丢了 20–35%**。

同一批短录音全部完整：18.8 秒→63 字（句号收尾）、11.7 秒→46 字、8.6 秒→25 字。
**分界线在 30 秒附近，正是 Whisper 单解码窗口的长度。**

vendored WhisperKit 里查到两个待验证的机制，尚未定位到确切成因：

1. **两处独立的 1 秒悬崖**：`AudioChunker.swift:81` 与 `TranscribeTask.swift:116`
   都是 `while … < …End - windowPadding`（`windowPadding = 16000` = 1.0 秒）。
   解码那处**按 VAD 分块逐块生效**，因此两块的录音丢的是 2 秒而非 1 秒——
   块数随时长增长，丢失量也随之增长。这与 M1 发现的短音频悬崖同源。
2. **每窗 224 token 的硬上限**：`Constants.maxTokenContext = Int(448 / 2)` = 224，
   `TextDecoder.swift:685` 在 223 处硬停，而 `DecodingOptions.sampleLength`
   默认就取这个值。**我们的 prompt 前缀占用同一份预算。**

**第 2 条牵连到 M5 的一个决定**：2026-08-17 把 prompt 从 63 字加长到 124 字，
吃掉的正是这 224 token 里的更大一块——**可能让长音频截断变严重了**。

**基准集查不出这个问题**：23 条里最长的「长句与标点」类是 15–30 秒，
**恰好顶到边界但从不越过**。基准集在 30 秒以上零覆盖，这是 M5 度量能力的
一个盲区。

**复现路径（便宜）**：M5 建的工具正好能查——TTS 合成一段 40–60 秒音频，
经 `BenchRunnerTests` 走生产管线，比对输出字数；再对 prompt 长度与
`sampleLength` 做二分。**修之前必须先复现**，上面两条都是推断而非结论。

顺带把 30 秒以上的样本补进 manifest，堵住这个盲区。

**① 注入失败与目标应用改变 → 剪贴板兜底 + 系统通知**

设计文档规则二、规则三都明确要求「写入剪贴板 + 系统通知」，**两条路都没做**：

- `UNUserNotification` / `NSUserNotification` **全仓零引用**
- `ClipboardSink` 只在「长文本超阈值」这一条路上用；权限被拒
  （`accessibilityDenied`）与目标应用改变时，文本**直接蒸发**

2026-08-17 真机上就撞到过：打包重签名作废了辅助功能授权，
`会话出错：accessibilityDenied`，说的话没落地也没留下副本。

M4 把「说完就切走」的窗口从 1–2 秒拉到 4–10 秒，规则三这条从边缘情形
变成了日常动作。

**② `retry()` 接上 UI 入口**

`Sources/vInput/Transcribe/Transcriber.swift:17` 的注释写着「**目前没有
任何 UI 入口**」——全仓只有测试在调它。转写失败时音频保留了，但用户点不到。
设计文档承诺的「一键重试」缺了一半。

**③ HUD 标注「本次未校正」**

模型加载中、解析不出替换、被闸门全拦——三种情况用户都只看到「没变化」，
无从判断是哪一种。设计文档规则二的表格本就要求 HUD 标注。
这是上手体验最大的缺口（三轮 QA 里两轮都提了，编号 O1）。

**④ 固定签名身份**

ad-hoc 签名的指纹随二进制变化，每次打包作废辅助功能与输入监控授权。
2026-08-17 一天内坑了三次。`scripts/build-app.sh` 的检测逻辑早已写好，
只差那张自签名证书被标记为可信（需要用户执行一条 `security` 命令，
见 `docs/dev-signing.md`）。

### M5 独立验收结转的两条

- **补技术类留出样本**（来自 M5 验收 B1）：基准集的技术术语被逐字写进了
  生产 prompt，`BenchMetrics.technicalTerms` 又是从参考文本抽词，于是
  「术语命中率」量的是 prompt 里有没有这个词。留出实验实测：同长同结构的
  prompt，术语未点名时技术类 CER 0.0584，点名后 0.0254——**79% 的改善来自
  把答案写进 prompt**。术语命中率现已恒为 1.000，天花板已达，这一格
  **失去分辨力**，暴露不了技术词回归。修法是补 2–3 条术语刻意不写进 prompt
  的技术样本（需用户补录，几分钟）。
- **`benchIsRecording` 可卡死导致听写被永久拒绝**（来自 M5 验收 L1）：
  忙碌 guard 放在停止分支之前，听写非 idle 时连「结束录音」都点不动；
  遥控器启动路径又漏查 `benchIsRecording`。触发后麦克风继续开着、日志谎报
  「已停止」、状态卡住且无 UI 可清。**仅 `VINPUT_BENCH=1` + 遥控器下可达**，
  分发版本 `benchEnabled` 恒 false，因此不阻塞 M5 合并。修法约三行。

### 两项待定，不在精简范围内但值得权衡

- **换模型/开关校正时重复加载 2 GB**（QA 编号 I6）：旧 `MLXCorrector`
  实例的加载无人取消，两份模型可能同时驻留。**16 GB 机器上这是可靠性
  问题而非体验问题**——逼近换页会让整机变慢。若 M6 期间观察到内存压力，
  应当纳入。
- **注入延迟**：见 `docs/M5-Backlog.md` 第一节。属于体验而非可靠性，
  且现在有基准集可以量化后再决定怎么解。

## M7 蓝牙鼠标接入

用户新购一支带收音功能的蓝牙鼠标，作为第三个音频源。

**架构上已经留好了位置。** M3 的设计决定是把遥控器与内置麦的全部差异吸收
在 `AudioSource` protocol 之后，上面各层不知道音频从哪来。新增音频源理论上
只需实现这一个 protocol，`AudioSourceRouter` 已支持多源路由。

### 动手前必须先查清的一件事

**这支鼠标的音频以什么形式送达？** 这决定工作量差一个数量级：

| 形式 | 工作量 |
|---|---|
| 注册成标准蓝牙音频输入设备（系统「输入」里能看到） | **小**。`SystemMicSource` 加一个设备选择即可，不碰 BLE |
| 私有 BLE 协议（像 RC003 的 ATVV） | **大**。等于重做一遍 M3：抓协议、解码、状态机 |
| USB HID / 厂商 SDK | 视情况 |

**先插上看系统设置里的「声音 → 输入」有没有它**，再决定路线。别在没查清
之前写任何代码。

### 其余待明确

- 触发方式：鼠标上哪个键？按住说话还是按一下开始/再按结束？
- 与现有两个音频源如何共存：自动选择还是手动切换？
- 断连、电量、多设备并存的处理

## M8 场景风格与润色层

三个 profile（技术 / 口语 / 书面）按前台应用的 bundle ID 切换，
完整标点、分段、去口水词。

### 两个必须先解决的设计问题

**1. 没有闸门时靠什么保证不改变原意？**

M4 的安全网是拼音闸门——同音才准改，机器可验证。**润色天然要改读音**
（加标点、去口水词、改书面语），闸门完全用不上。

这个风险 M4 期间实测发生过：模型建议过 `小米→米粒`、`情况→状况`；
某一版提示词让 `小米遥控器→小米耀空气` **真的被应用了**（同音，闸门放行）。
没有闸门，这些会直接落到用户的文字里。

**2. 本地模型做不做得了？**

用户提出的判断：Qwen3-4B 连「只改同音错字」这个更简单的任务都吃力
（六段测试修对 1 次），而润色是带风格约束的语义改写，难度高一个量级。
**能力更弱的模型配更弱的安全网**，是个危险组合。

应当重新评估原始设计里那条「可插拔，默认本地，云端可选」——M4 选了只做
本地，对校正是对的（有闸门兜着），对润色可能不成立。

## M9 分发准备

从 M6 推迟过来的、「准备给别人用」才需要的：

- 设置界面（profile 编辑、模型选择、各项开关的统一入口）
- 权限引导 / onboarding（首次启动引导授权与模型下载）
- 长文本剪贴板路径的实际验证（`RoutingTextSink` 有 100 字阈值，未验证过
  长文本的真实表现）

**推迟的理由**：产品目前只有作者一个用户。这些需求等真要分发时会更清楚，
现在做容易做出一个届时要推翻的东西——与 M4 把润色推迟到有场景之后是
同一个判断。
