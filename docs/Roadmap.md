## 与原始设计的差异及理由

**原 M4「润色层」收窄为「校正层」，润色并入后续。**
润色的正确答案依赖场景——同一句话在 Cursor 里该保留术语原文，在微信里该保留
口语感。脱离场景做，会做出一个后续必须推翻的东西。

**原 M5「场景风格」顺延，M5 改做转写质量。**
M4 收尾的真机数据：六段标准测试**七个错误只有一个是下游能修的**，其余全是
转写层的漏字、听错、大小写；而下游看不到音频，声学证据已经没了。在转写层
不够好的时候做润色，等于在一段已经错了的文字上精修排版。

**M7 蓝牙鼠标插在 M6 与润色之间**（2026-08-16 决定）。

## M6 稳固化（精简版）

**2026-08-17 决定：M6 只做可靠性，分发相关的功能推到 M9。**

理由：产品目前只有一个用户（作者本人）且已在日常使用。设置界面、onboarding
这类是「准备给别人用」才需要的，而「用着用着话就没了」是每天都在发生的。
先把可靠性做到位，分发的需求等真要分发时也会更清楚。

### 四项（按现状核实过，不是照抄原设计）

**⓪ 超过约 30 秒的语音被静默截断（2026-08-17 用户报告，日志已确认）**

**这是主路径上的静默丢字，优先级高于下面四项。**

真机证据，session 103：

```
16:03:17.983  遥控器语音键按下，开始录音
16:03:27.926  ATVV MIC_EXTEND request      ← 三次续期
16:03:37.926  ATVV MIC_EXTEND request
16:03:47.926  ATVV MIC_EXTEND request
16:03:49.421  遥控器语音键松开，进入转写
16:03:59.679  本次能量：304 个块 超阈值 145 个 (47%)
16:03:59.679  注入成功 文本(81字): …我在想,有没有可能把 M8 的分场景优化改成?
```

**31.4 秒只出 81 字，且断在半句上**——「改成**?**」后面没了。按用户基准集
实测语速 3.1–4.6 字/秒，31.4 秒应有 100–140 字，**丢了 20–35%**。

同一批短录音全部完整：18.8 秒→63 字（句号收尾）、11.7 秒→46 字、8.6 秒→25 字。
**分界线在 30 秒附近**（当时以为是单解码窗口的长度，实测是 VAD 分块的
触发点，见下）。

**基准集查不出这个问题**：23 条里最长的「长句与标点」类是 15–30 秒，
**恰好顶到边界但从不越过**。基准集在 30 秒以上零覆盖，这是 M5 度量能力的
一个盲区。

#### 已复现并定位（2026-08-17，`./scripts/long-audio.sh`）

原先列的两个待验证机制**都不是主因**，主因是第三个：
**VAD 分块把连续语音切在句子中间，切中的那一块整块被判死。**

链条（全部走生产 `WhisperKitTranscriber`，turbo，探针实测）：

1. `WhisperKit.swift:1021` 只在 `音频长度 > windowSamples`（= 30 秒）时才
   启用 `chunkingStrategy: .vad`。**30 秒的分界线来自这里**，不是解码窗口。
2. `VADAudioChunker.splitOnMiddleOfLongestSilence` 在后半段找最长静音取中点。
   一口气说完、句间没有停顿时，那个「最长静音」就落在句子中间。
3. 每块**独立**走一遍 `runTranscribeTask`，各自退火，块与块之间没有上下文。
   切在句中的那块开头，模型接不上前文。
4. `firstTokenLogProbThreshold = -1.5`（`Configurations.swift:215`）：首个采样
   token 的 logProb 低于它就整窗作废（`Models.swift:367` 把它列为第一优先的
   `needsFallback`）。实测那一块的首 token logProb = **−1.86**。
5. 六档温度依次失败后，`decodeWithFallback` **不保留过程中最好的一次**，
   只返回最后一次。最后一次恰好又是「首 token 太低、零个 token」那种，
   于是**整块 15.6 秒的语音变成空字符串**——不报错、不记日志。

一段 31.0 秒 / 148 字的实测退火全过程：

```
temp 0.0  首 token −1.86 < −1.5  → firstTokenLogProbThreshold，采样 0 个 token
temp 0.2  采样 92 token          → avgLogProb −11.37 < −1.0，logProbThreshold
temp 0.4  采样 156 token 撞满 224 上限 → avgLogProb −2.28，logProbThreshold
temp 0.6  采样 74 token，内容其实是对的 → avgLogProb −1.074，差 0.074 没过
temp 0.8  首 token −3.05         → firstTokenLogProbThreshold，采样 0 个 token
temp 1.0  首 token −2.89         → 温度用完，就用这一次的结果 → 整块空
```

**它是间歇性的**：同一段音频、同一个模型、温度 0，连续跑 8 次
**3 次丢、5 次正常**；换一轮又是 4/5、0/5。Core ML 在 ANE 上的浮点抖动
足够让 −1.86 在 −1.5 阈值两侧来回。这解释了为什么用户不是每次都撞上，
也解释了为什么单跑一次的测试会报绿。

**临时关掉 VAD 分块，同一段音频 0.554 → 1.000**（CER 0.50 → 0.014）。
不分块时走 Whisper 原生滑窗：窗口解到 27.82 秒的**句子边界**，下一窗从那里
续上，永远不会在句中冷启动。VAD 分块把这个机制拆掉了。

现象数据（生产默认 prompt，覆盖率 = 实际字数 / 参考字数）：

| 语料 | 11–26 秒 | 31 秒 | 43 秒 | 60 秒 | 88 秒 |
|---|---|---|---|---|---|
| 带停顿（4.0 字/秒） | 0.98–0.99 | 0.99 | 0.99 | 1.00 | 1.00 |
| 一口气说（4.8 字/秒） | 1.00 | **0.50**（间歇） | 0.95 | 0.97 | 0.98 |

**丢失量不随时长单调增长**——它取决于切点落在哪里，31 秒那条最容易翻车，
43/60/88 秒反而没事。这否掉了「块数随时长增长、丢失量随之增长」的推断。

#### 原先那两条假设的实测结论

**1 秒悬崖：真实存在，但量级解释不了 20–35%。** 两处 `windowPadding` 确实
各砍掉末尾 1 秒，但 `findSeekPointAndSegments` 通常把 seek 直接推到块尾，
循环自然结束，实测没有因此丢字。上限是每块末尾 ≤1 秒。

**224 token 硬上限：成立，已量化，但真人语速下还没踩到。**
`prefillDecoderInputs` 把 prompt 拼进 `initialPrompt`，`TextDecoder.swift:685`
在 `currentTokens.count >= 223` 处硬停，两者共用同一份预算：

| prompt | prefill token 数 | 每窗可采样 | 24 秒 180 字 | 27 秒 206 字 |
|---|---|---|---|---|
| P6 现行（124 字） | 67 | **156** | 0.883 | 0.772 |
| P0 旧版（63 字） | 40 | 183 | 1.000 | 0.913 |
| 不挂 prompt | 4 | 219 | 1.000 | 0.976 |

这一格是**确定性**的，不像上面那条要靠运气。但要撞到它得 7.6 字/秒——
真人上限 4.6 字/秒 × 30 秒 ≈ 140 字 ≈ 145 token，**在 156 的预算内，
余量约 10 个字**。所以：**P6 没有造成用户遇到的那次截断，但它把余量从
27 个字压到了 10 个字**，说话再快一点、或者再加长 prompt 就会踩上。

`sampleLength` 调大没有用——`loopCount` 取 `min(…, maxTokenContext - 1)`，
224 是 KV cache 的编译期尺寸，改不动。

#### 修法已选定：关掉 VAD 分块（2026-08-17，`./scripts/decode-sweep.sh`）

**最对症的那个修法本轮不可用**：`decodeWithFallback` 每轮覆盖
`decodingResult`、返回最后一次而非最好的一次，改它要动
`vendor/WhisperKit`，而 `vendor/` 在 `.gitignore` 里——改了不进版本库、
换机器就没、而且没人看得见。所以只在 `DecodingOptions` 这几个旋钮里选。

**争议点从来不是「哪个能治丢字」，而是「代价是多少」**：候选里三个动的
都是防幻觉机制。因此对照必须同时量三维——长语音丢不丢字、静音会不会
冒话、日常语料退不退化。**只报一维等于没测。**

每个变体相对现状**只动一处**（组合变体另列），dense-31 每档重复 12 次
（该 bug 是间歇性的，单次结果没有意义），静音/底噪每档 24 次：

| 变体 | dense-31 失败 | 长语料失败 | 静音非空 | 基准集 CER |
|---|---|---|---|---|
| 现状（vad on，首 token −1.5） | 4/12、6/12 | 6/37、8/37 | 0/24、0/24 | 0.0190 |
| **关 VAD 分块（已采纳）** | **0/12、0/12** | 2/37、2/37 | **1/24、0/24** | 0.0190 |
| 关首 token 阈值 | 0/12 | 2/37 | **12/24** | 0.0190 |
| 首 token 阈值放宽到 −3.0 | 0/12 | 2/37 | **10/24** | 0.0190 |
| 关分块 + 关首 token 阈值 | 0/12 | 2/37 | **16/24** | 0.0190 |
| 关首 token 阈值 + 不退火 | 0/12 | 2/37 | **12/24** | 0.0190 |
| 空块救援（见下） | 0/12 | 2/37 | 2/24 | 0.0190 |

（两个数的格子是两轮独立采样。「长语料失败」里恒定的那 2/37 是 budget-24
与 budget-27，属于 224 token 预算那条**另一个**确定性问题，与本条无关。）

**四个候选都能把 dense-31 打到 0/12，区别全在代价。** 动
`firstTokenLogProbThreshold` 的三档把静音幻觉从 0 拉到 10–16 次，漏出来的
正是这个产品一直在防的那一类：「谢谢大家。」「好,谢谢。」，以及
「请不吝点赞 讨订阅 转发 打赏支持明镜与点点栏目」。**那是拿一种丢字换
另一种丢字。** 关分块两轮只漏 1 次「谢谢。」，是唯一便宜的。

**实测掉的两个顾虑**（`./scripts/decode-sweep.sh --scaling`）：

```
3min  176.8s   on 27.6s (6.4x)   off 25.2s (7.0x)
6min  353.6s   on 57.3s (6.2x)   off 59.1s (6.0x)
10min 618.8s   on 111.1s (5.6x)  off 109.8s (5.6x)
峰值：整个测试进程 maximum resident set size 669 MB、peak footprint 48 MB
```

**耗时与内存都没有差别。** 这一条反直觉，值得记住原因：分块那条路把各块
丢进 `TaskGroup` 并发解码（`WhisperKit.swift:803-870`，macOS 上 16 个
worker），不分块走串行滑窗，**看代码会以为长录音要变慢**。实际不会——
ANE 是一块硬件，并发 worker 照样在它上面排队，并行度买不到吞吐。
内存也不涨：mel 与 encoder 都在窗口循环内部逐窗算
（`TranscribeTask.swift:114-146`），整段驻留的只有原始 float 数组。

**方法论上踩到的一个坑，别再踩**：M5 那套静音素材里 `silence30` 恰好是
30.0 秒，而分块的触发条件是「严格大于 30 秒」（`WhisperKit.swift:1021`），
**拿它比较分块 on/off，两边跑的是同一条代码路径**。本轮补了 45 秒静音与
底噪、以及「真人说 14.7 秒 + 尾部静音 20 秒」这个生产上最常见的形态。

#### 备胎：空块救援（不碰 vendor 地「保留最好的一次」）

已实现但**默认关闭**（`DecodeTuning.rescueEmptyChunks`）。留档是因为它
回答了一个看上去不可能的问题：那个丢弃发生在私有的 `decodeWithFallback`
里，但**被丢弃的东西是一整块，而分块机器全是公开的**——
`VADAudioChunker`（`open class`）、`chunkAll`、`EnergyVAD`、`AudioChunk`、
`transcribe(audioArray:audioArrayOffset:decodeOptions:)` 都是 public。

于是照抄 `WhisperKit.swift:1021-1046` 的参数（`maxChunkLength =
featureExtractor.windowSamples`、默认 `windowPadding` 16000、默认
`EnergyVAD`）在我们这一层自己切一遍，逐块解码，**块的边界就落进了我们
自己的代码**，能在拼接之前看见每一块的结果。某块解出空文本时，只对那一块
用 `firstTokenLogProbThreshold: nil` 重解一次。

**便宜在那道闸**：重试还要求这一块的 `EnergyVAD` 活跃帧占比 ≥ 10%
（真人说话实测约 47%，纯静音是 0）。静音块解出空是**正确答案**，永不重试，
所以默认路径上每一道防幻觉机制都原样保留。每次救援都记日志——原本的失败
形态是「不报错、不记日志、话就没了」，这正是它难查的原因。

**没有采纳它，是因为对照表里它并不比关分块更好**（静音 2/24 对 1/24），
而它多一条自己维护的分块代码路径。若将来关分块出现别的副作用，它是现成的
第二方案。

回归测试留在 `Tests/vInputTests/LongAudioTests.swift`，门控同 `BenchRunnerTests`
（标记文件，不进日常 `./scripts/test.sh`）：

```bash
./scripts/long-audio.sh          # 约 10 分钟，报告出到 Bench/long-audio.txt
```

**dense 组报绿不等于修好了**——失败率两到八成，判「修好」要三个变体
连续两轮零失败；budget 组是确定性的，一次红就是红。

顺带把 30 秒以上的真人样本补进 manifest（需用户补录），堵住基准集这个盲区。

#### 新发现的待办：几分钟量级的录音覆盖率存疑（2026-08-17，未定论）

`--scaling` 那一轮顺带量到的，**不是本条 bug，也还没有定论**：

| 时长 | 分块 on 覆盖率 | 分块 off 覆盖率 |
|---|---|---|
| 3 分钟 | 0.673 | 0.844 |
| 6 分钟 | 0.761 | 0.778 |
| 10 分钟 | 0.664 | 0.521 |

**先说这批数字的局限，它比数字本身重要**：每档**只跑了一次**；音频是把
`dense-91` 首尾相接复制 2/4/7 遍造出来的，**整段是同一段话在重复**，而
`compressionRatioThreshold = 2.4` 恰恰会把「输出太重复」判为失败并触发退火。
也就是说**这个语料在构造上就对 Whisper 不利，绝对值很可能偏悲观**。
**不要把 0.521 当成结论**——要下结论得用不重复的长语料重测，且每档多跑几次。

可达性把这三档分成了两半（已在仓库内核对）：

- 遥控器路径够不到 3 分钟以上：**RC003 固件在整 60 秒切断**，`MIC_EXTEND`
  拦不住（`Testing/M3-Acceptance.md:127` 实测 60.04 秒）。
- 我们自己的上限是 `VoiceSessionKeepalive.maxDuration = 180`（3 分钟）。

**所以 6 分钟与 10 分钟两档是录不出来的场景**，那里 off 输给 on
（0.521 对 0.664）不构成否决关分块的理由。唯一勉强可达的 3 分钟档，
**off 明显更好（0.844 对 0.673）**。而在真实可达范围内（长语料 ≤88 秒），
关分块是 dense 全组 1.000、paced 0.979–0.997。

待办两条：

1. 用**不重复**的长语料把 2–3 分钟这一档重测，每档多跑几次，确认
   0.844 是真的（说满 3 分钟丢约六分之一）还是合成语料的假象。
2. 若属实，Option+D 这条路（遥控器够不着，但键盘够得着 180 秒）应该给一个
   可达的时长上限或临近提示，**而不是让用户在不知情的情况下丢字**——
   这与 M6 ⓪ 本身是同一类问题：静默丢字比报错更糟。

**① 注入失败与目标应用改变 → 剪贴板兜底 + 系统通知**

设计文档规则二、规则三都明确要求「写入剪贴板 + 系统通知」，**两条路都没做**：

- `UNUserNotification` / `NSUserNotification` **全仓零引用**
- `ClipboardSink` 只在「长文本超阈值」这一条路上用；权限被拒
  （`accessibilityDenied`）与目标应用改变时，文本**直接蒸发**

2026-08-17 真机上就撞到过：打包重签名作废了辅助功能授权，
`会话出错：accessibilityDenied`，说的话没落地也没留下副本。

M4 把「说完就切走」的窗口从 1–2 秒拉到 4–10 秒，规则三这条从边缘情形
变成了日常动作。

**用户 2026-08-17 定的**：走**系统通知**（不是只让 HUD 变红）。
理由是规则三触发时用户人已经在别的应用里，HUD 未必在视野内，通知是唯一
还能触达的方式。通知**只提示、不代劳**——文字已在剪贴板，用户自己 Cmd+V。

不做「点通知自动重新注入」：点通知会把 vInput 拉到前台，**反而把注入目标
变成我们自己**，时序脆弱且容易注错地方。

两个连带问题，实现时必须处理：

- **通知要授权，而这是个新弹窗**（与辅助功能不同，不会被重签名作废，
  授权一次长期有效）。若用户拒了或点掉了，这条兜底就静默失效——**而那
  正是本条要修的那类问题**。因此发通知前先查授权状态，**未授权就退回
  HUD 提示并写日志**，不许无声消失。
- **写剪贴板会覆盖用户原有内容**。这是「救回文字」的必然代价，但通知里
  要带上文字开头，让用户知道剪贴板现在是什么。是否改成「仅在剪贴板为空
  或内容是我们上次写的时才覆盖」尚未定——那样更保守，但会出现「既没注进去
  也没进剪贴板」的白救情形。**当前决定：直接覆盖 + 通知告知。**

**② `retry()` 接上 UI 入口**

`Sources/vInput/Transcribe/Transcriber.swift:17` 的注释写着「**目前没有
任何 UI 入口**」——全仓只有测试在调它。转写失败时音频保留了，但用户点不到。
设计文档承诺的「一键重试」缺了一半。

**用户 2026-08-17 定的**：入口放**菜单栏**。理由是状态一直可见、不占用新的

### ⑤ 中文语境下标点是半角（2026-08-17 用户报告）

说中文时输出的是半角 `,`，句号却是全角 `。`。用户希望中文语境用全角标点。
日志里问号同样：`把 M8 的分场景优化改成?`——一句话里两种宽度混着。

**范围（2026-08-17 用户定，先只做逗号、当天扩到全部）**：
`, ? ! : ;` 加上成对的 `( )`，**不含句号**。已做完，见下面「实际做到的范围」。

**用户原本建议记进 M8，我改记 M6——因为这个修法一个模型都不需要。**
M8 的前提是「本地模型做不了，得上云端」；全半角转换是转写后的字符替换，
落在 `TranscriptCleaner` 里即可（该文件已在做去特殊 token、剥字幕署名）。
等三个里程碑不划算。

**不能靠改 prompt 修，那条路实测会炸。** `WhisperKitTranscriber.swift:164`
记着：全角「，」是 UTF-8 三字节（EF BC 8C），用全角的 prompt 候选在 24 秒的
long.wav 上**稳定复现**同前缀字节级乱码（`Ｂ` EF BC A2、`４` EF BC 94、`�`），
换成半角后 90 次转写零乱码。Whisper 跟着 prompt 的习惯走，输出也就成了半角。

**度量看不见这件事——第三个盲区。** 基准集 23 条标准文本里 20 个逗号
**全是全角**，转写输出**全是半角**，而 `characterErrorRate` **刻意排除标点**
（「一次标点改善会掩盖一次真实的漏字」），`punctuationCount` 只数个数不分
全半角。这个不匹配从第一天就在基准集里，度量完全屏蔽了它。

因此修法要含两部分：

1. `TranscriptCleaner` 里做中文语境的全半角转换。**难点是中英混排**——
   `用 Claude Code 部署到 AWS,先跑 npm install` 里那个逗号该转全角（中文
   语境），英文短语内部的逗号该保持半角。与 `CorrectionGate.joiningLatinWords`
   处理拉丁词边界同类，有现成路子可循。
2. **给度量补一个能看见全半角的指标**，否则它会再次无声退化——
   这正是前两个盲区的教训。

**实际做到的范围**（`ChineseScript.fullWidthConversions`）：

| 字符 | 判据 | 改写 | 度量 |
| --- | --- | --- | --- |
| `, ? ! : ;` | 邻居规则 | ✅ | ✅ |
| `( )` | 成对规则 | ✅ | ✅ |
| `.` | 邻居规则 | ❌ | ✅ |
| `" '` | —— | ❌ | ❌ |

**邻居规则**：跳过空白后离标点最近的那个实字符，两侧任一处在「中文语境」
就转全角，并吃掉紧邻的空白（换行不吃，它是内容边界）。中文语境 =
汉字 / CJK 符号标点 `U+3000–303F` / 全角形式 `U+FF00–FFEF`；弯引号
`U+2018–201D` **不算**（英文同样在用它们）。这条同时挡住了最贵的误伤：
千分位 `1,200,000` 两侧都是数字，一个字不动；`3:30`、`16:9`、
`https://x.com/s?q=1` 同理。

**括号必须另立一条，不能照搬邻居规则。** 括号在代码、路径、函数签名里极常见
而且**成对**：`函数 foo(x) 的返回值` 里左括号前邻是拉丁、右括号后邻是汉字，
邻居规则会把这一对拆成一半一全。三条同时满足才转：

1. **成对**——配不上的一半一律不动（不成对时括号范围未知，也就无从判断
   里面是什么，而 Whisper 漏掉一半括号是常事）；
2. **括号内有中文、且没有拉丁字母**——数字放行，`（见 2.1 节）` 是正常中文
   行文，一刀切禁数字会漏掉一大类；`(large-v3-turbo)` 有字母，不转；
3. **括号外没有拉丁字母或数字粘着，且两侧至少一处是中文语境**——
   `/usr/local/bin(不要改)` 与 `render(这里传中文)` 的粘连是函数调用与路径的
   形状，中文行文里几乎不这么写（会写成「路径是 …/bin（不要改）」或至少留
   个空格），判成代码保持半角。孤零零的 `(不要改)` 外部没有中文邻居，
   多半是被截断的代码片段，也不转。

**句号刻意不改**：用户点名的是五个，句号不在其列；而且它不该顺手加进来——
`我想想...` 的三个点各自都满足邻居规则，转完是「我想想。。。」。度量照数它，
「度量该看见全部，改不改是另一个决定」。

**已知误伤，记在这里**：`写成 int x = 1; 然后编译` 里的分号会被转成全角。
这是**邻居规则本身的代价**，不是漏写的分支——它与 `部署到 AWS,先跑 npm install`
（该转）的形状一模一样，只看邻居分不开。括号靠成对判断绕开了同类问题，
`; : ? !` 没有「对」可配，绕不开。接受的理由是口述中文时说出 `;` 的场景极少，
且误伤只发生在「代码片段紧接中文」这一种排布上；真出问题时先收窄分号与冒号。
`Tests/vInputTests/PunctuationWidthTests.swift` 里有一条测试专门钉住这个行为。

**度量与转换器共用同一个函数**（`ChineseScript.fullWidthConversions`），不是
各写一遍同一条规则：括号的判据复杂得多，各写必然分叉，而分叉的两个方向都
致命——「转换器改了但度量看不见」，以及「度量把转换器刻意不改的代码括号记成
退化」（指标从此恒不为零，没人会再看它）。

### M5 独立验收结转的两条

- **补技术类留出样本**（来自 M5 验收 B1）：基准集的技术术语被逐字写进了
  生产 prompt，`BenchMetrics.technicalTerms` 又是从参考文本抽词，于是
  「术语命中率」量的是 prompt 里有没有这个词。留出实验实测：同长同结构的
  prompt，术语未点名时技术类 CER 0.0584，点名后 0.0254——**79% 的改善来自
  把答案写进 prompt**。术语命中率现已恒为 1.000，天花板已达，这一格
  **失去分辨力**，暴露不了技术词回归。修法是补 2–3 条术语刻意不写进 prompt
  的技术样本（需用户补录，几分钟）。
- **`benchIsRecording` 可卡死导致听写被永久拒绝**（来自 M5 验收 L1）：
  忙碌 guard 放在停止分支之前，听写非 idle 时连「结束录音」都点不动；
  遥控器启动路径又漏查 `benchIsRecording`。触发后麦克风继续开着、日志谎报
  「已停止」、状态卡住且无 UI 可清。**仅 `VINPUT_BENCH=1` + 遥控器下可达**，
  分发版本 `benchEnabled` 恒 false，因此不阻塞 M5 合并。修法约三行。

## M7 蓝牙鼠标接入

用户新购一支带收音功能的蓝牙鼠标，作为第三个音频源。

**架构上已经留好了位置。** M3 的设计决定是把遥控器与内置麦的全部差异吸收
在 `AudioSource` protocol 之后，上面各层不知道音频从哪来。新增音频源理论上
只需实现这一个 protocol，`AudioSourceRouter` 已支持多源路由。

### 动手前必须先查清的一件事

**这支鼠标的音频以什么形式送达？** 这决定工作量差一个数量级：

| 形式 | 工作量 |
|---|---|
| 注册成标准蓝牙音频输入设备（系统「输入」里能看到） | **小**。`SystemMicSource` 加一个设备选择即可，不碰 BLE |
| 私有 BLE 协议（像 RC003 的 ATVV） | **大**。等于重做一遍 M3：抓协议、解码、状态机 |
| USB HID / 厂商 SDK | 视情况 |

**先插上看系统设置里的「声音 → 输入」有没有它**，再决定路线。别在没查清
之前写任何代码。

### 其余待明确

- 触发方式：鼠标上哪个键？按住说话还是按一下开始/再按结束？

- 断连、电量、多设备并存的处理

## M8 场景风格、润色与多语种输出

三个 profile（技术 / 口语 / 书面）按前台应用的 bundle ID 切换，
完整标点、分段、去口水词。

### 大原则（2026-08-17 用户确立）：一切不出本机

**理由是用户给的：未来会用它口述机密内容，包括报价。**

这条**收紧**了原始设计的「音频不落盘」——现在是内容本身也不出本机，
不只是音频文件。它与同日选定 Gemini 的决定**直接冲突**，M8 设计时必须
正面处理，不能两条都记着当没看见。

**冲突比表面更尖锐**：最需要翻译的场景与最机密的内容是同一批。要把报价
发给国外客户，那句话既是要翻译的、也是不能出机的。「本地转写 + 云端翻译」
这个分工恰好把最敏感的内容挑出来送了出去。

按目标语言分，可行性完全不同：

| | 本地可行性 |
|---|---|
| 中 → 英 | **可以**。WhisperKit 的 `task: .translate` 由 Whisper 自己完成，纯本机，一个参数的距离 |
| 中 → 西 | Whisper 做不到。只能本地 LLM（未测量）或云端 |
| 场景润色 | 本地 4B 已实测吃力；8B / 14B **未测量** |

用户的直觉「多语言不出本机可能性不大」**对西语成立，对英语不成立**。

因此 M8 应当先穷尽本地路径再谈云端：先试 Whisper 原生 translate（中→英），
再用基准集测本地 8B/14B 能否胜任西语与润色。**云端是兜底，不是默认。**
若最终仍需云端，它必须是显式的、每次可见的、可关闭的——而不是某个 profile
自动触发。

**2026-08-17 扩大范围：把「翻译成其他语言」并入 M8。**

用户提出想把中文语音输出成英语 / 西语文字。现状核实：**完全不支持**，
代码从未设置 `DecodingOptions.task`，走默认的 `.transcribe`。

分两种情形，差别很大：

- **中文 → 英语**：WhisperKit 有 `task: .translate`，技术上就是改一个参数。
  但 `punctuationPrompt` 是中文的、`normalizeToSimplified` 与
  `TranscriptCleaner` 都按中文输出写、拼音闸门对英文无意义、
  **基准集全是中文参考文本因此零度量能力**。
- **中文 → 西语**：**Whisper 做不到。** WhisperKit 自己的注释写死了
  （`Configurations.swift:135`）：`translate` 是 X→**English**，
  没有其他目标语言。这是模型能力边界，不是参数问题。

因此翻译与润色是同一类操作——都要重写文本、都过不了拼音闸门、
都需要更强的模型。**应当共用同一套安全网，并入 M8 一起设计。**

### 后端选型：Codex CLI 实测不可行

用户提议复用本机已装的 `codex` CLI（0.145.0，有非交互的 `codex exec`），
省掉 API key 管理。**实测否决**（2026-08-17，翻译一句 46 字中文）：

| 配置 | 耗时 | 结果 |
|---|---|---|
| 默认（`reasoning effort: high`） | **39.8 秒** | 译文正确，用掉 6,608 token |
| `model_reasoning_effort=minimal` | **29.7 秒** | 失败（exit 1，无输出，未深究） |

译文质量确实好（「scenario-specific optimizations」这种译法本地 4B 给不出）。
**问题不在质量，在形状**：

- **约 30 秒是固定开销的地板**，不是推理慢——启进程、装 skills、刷模型列表
  （首次跑还超时报错）、跑 agent 循环。降到最低推理档一秒没省下来。
- **一句话 6,608 token**，绝大部分是 agent 脚手架，等于每次听写都啃掉
  用户 Codex 额度的一大块。
- 它是带沙箱和工具调用的 **agent 循环**，我们要的是一次文本补全。
- 0.145.0 版本号仍在快速变动，输出格式不是稳定接口。

**改为直接调 API**，一次 HTTPS POST，一段话约 1–3 秒，key 放 Keychain。
后端应做成可插拔，让「换更强的本地模型」这条路留着——用户
「本地肯定做不成」是合理推测但未经测量，而 M5 之后我们有能力测量它。

**2026-08-17：用户选定 Gemini。** 翻译是它的强项，免费额度对个人用量够用。

注意 Gemini 的 API 形状与 Anthropic / OpenAI 的 messages 接口不同
（`generateContent`、`contents`/`parts` 结构），可插拔后端的接口设计要能容纳
这个差异，不能照着 messages 接口的形状硬套。

### API key 的存放：不进对话、不进仓库

**key 由用户自己放进 Keychain，任何时候都不要贴进对话。** 对话记录以明文
长期留在 `~/.claude/projects/…/*.jsonl`；本仓库又在 OneDrive 下，提交即上云。
两条都是不该放密钥的地方。

M8 开工时由用户在终端执行（`-w` 后不带值，交互式输入，key 也不进 shell 历史）：

```
security add-generic-password -a vInput -s vinput-gemini-api-key -w
```

应用启动时从 Keychain 读，读不到就禁用云端后端并在 HUD 提示——**不要**
回退到「静默不工作」，那是 M6 ③ 正在修的同一类问题。

### 两个必须先解决的设计问题

**1. 没有闸门时靠什么保证不改变原意？**

M4 的安全网是拼音闸门——同音才准改，机器可验证。**润色天然要改读音**
（加标点、去口水词、改书面语），闸门完全用不上。

这个风险 M4 期间实测发生过：模型建议过 `小米→米粒`、`情况→状况`；
某一版提示词让 `小米遥控器→小米耀空气` **真的被应用了**（同音，闸门放行）。
没有闸门，这些会直接落到用户的文字里。

**2. 本地模型做不做得了？**

用户提出的判断：Qwen3-4B 连「只改同音错字」这个更简单的任务都吃力
（六段测试修对 1 次），而润色是带风格约束的语义改写，难度高一个量级。
**能力更弱的模型配更弱的安全网**，是个危险组合。

应当重新评估原始设计里那条「可插拔，默认本地，云端可选」——M4 选了只做
本地，对校正是对的（有闸门兜着），对润色可能不成立。

**换成云端强模型能提高「改得对」的概率，但不提供任何验证手段。**
M4 期间 `小米遥控器 → 小米耀空气` 是闸门放行的漏网之鱼；M8 连闸门都没有。
用更强的模型是把风险降低，不是消除——**这是 M8 brainstorming 的核心议题，
模型选型反而次要**。

**3. 隐私：这是产品性质的改变，需要一个明确决定**

原始设计是本地优先（「音频不落盘」是写进 spec 的原则）。把用户说的每句话
发到云端 API 与此冲突。这个决定应当被明确做出并写下理由，不能顺势滑过去。

**2026-08-17 用户选定 Gemini，等于对这条做出了决定：M8 的润色/翻译路径上，
用户的语音内容会发送给 Google。** 记在这里，是为了让它是一个被明确做出的
决定，而不是「因为选了某个 API 所以顺带发生了」。

仍需在 M8 设计时明确的：走云端的是**转写后的文本**还是音频（应为文本，
音频不出本机这条原则不必因此放弃）；是否保留一个「本次不走云端」的开关；
以及走了云端时 HUD 是否要有可见标识。

**4. 交互：翻译/润色是每次听写都做，还是显式模式？**

直接决定延迟预算。校正层是 8 秒（M4 实测定的）；若做成显式模式
（另一个快捷键，或遥控器的另一个键——`0x4F–0x52` 方向键与 `0xF1` 返回键
在 M3 期间都已抓到 HID usage 且当前无用途），预算可以宽松得多。

## M9 分发准备

从 M6 推迟过来的、「准备给别人用」才需要的：

- 设置界面（profile 编辑、模型选择、各项开关的统一入口）
- 权限引导 / onboarding（首次启动引导授权与模型下载）
- 长文本剪贴板路径的实际验证（`RoutingTextSink` 有 100 字阈值，未验证过
  长文本的真实表现）

**推迟的理由**：产品目前只有作者一个用户。这些需求等真要分发时会更清楚，
现在做容易做出一个届时要推翻的东西——与 M4 把润色推迟到有场景之后是
同一个判断。
