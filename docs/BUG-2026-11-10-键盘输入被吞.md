# BUG 2026-11-10：vInput 运行时，全系统键盘输入被吞

## 现象
- Mac mini 上，本机蓝牙键盘 Logi K580 打字没反应，通过 VNC（屏幕共享）远程打字也没反应。
- 鼠标正常。系统没有卡死：WindowServer 正常、负载低、内存还剩 35%，SSH 能登进去。
- 退出 vInput（`osascript -e 'quit app "vInput"'`）后，**立刻恢复**。

## 当时的状态
- 进程：`projects/vInput/dist/vInput.app/Contents/MacOS/vInput`，PID 85209，已连续运行约 1 天 13 小时（大约 2026-11-08 晚上启动）。
- 退出前的状态：`S`（正常休眠），CPU 0.4%，内存约 27 MB。说明它**没有死循环，也没有内存涨爆**。
- 它对退出命令反应正常（10:40:51 收到 terminate，15 毫秒内退出完毕）。说明主线程没卡死。
- 前台程序是「终端」。当前输入法：简体拼音（SCIM）和 `com.apple.inputmethod.ironwood`。

## 已经排除的原因
| 查了什么 | 结果 |
|---|---|
| 安全输入（Secure Input，专门防偷看密码的功能，开着时会拦下按键） | 没有程序占用 |
| 卡死、未响应的程序 | 没有 |
| 辅助功能里的键盘设置（慢速键、粘滞键、鼠标键） | 没开 |
| 系统输入法相关进程（SCIM_Extension、TextInputMenuAgent、imklaunchagent） | 10:38 重启过，**没有用** |
| 蓝牙键盘本身 | VNC 打字也不行，所以不是键盘的问题 |

## 系统日志（`log show --predicate 'process == "vInput"'`）
- 10:32–10:40 期间，主线程几乎每秒都在打印 `Loading Preferences From User CFPrefsD`，有时一秒好几次。看起来，**每次有输入事件，它都会去读一次偏好设置**（推断，需要对照代码确认）。
- 10:38:29 的三条 `XPC_ERROR_CONNECTION_INTERRUPTED`，是我手动重启系统输入法进程造成的，不是 vInput 自己出的错。
- 退出时有 `[com.apple.bluetooth:CoreBluetooth] XPC connection invalid`，说明 vInput 用到了 CoreBluetooth（苹果的蓝牙编程接口）。
- 日志里**没有**看到 vInput 自己打印的报错。

## 怀疑方向（都是推断，没看过源码，按可能性排）
1. **事件拦截（CGEventTap，在系统层面截获键盘事件的接口）的回调对键盘事件返回了 nil**，或者处于某种状态时没有把原事件放行，于是所有按键都被吞掉。
   - 查：回调里每一条分支（包括出错、状态不对、提前 return 的分支）是不是都 `return Unmanaged.passUnretained(event)`。
   - 查：有没有某个「模式 / 开关」卡在打开状态，导致一直在吞键，例如长按触发、录音中、等待模型回结果这类状态没有复位。
2. **拦截器被系统停掉后，处理不对**。回调太慢（比如在回调里读偏好设置、做同步工作）时，系统会发来 `kCGEventTapDisabledByTimeout`；用户输入异常时会发来 `kCGEventTapDisabledByUserInput`。
   - 查：收到这两个事件时，有没有重新调用 `CGEvent.tapEnable(tap:enable:true)`，并且把事件原样放行。
   - 查：回调里不要做读 `UserDefaults`、加锁、同步等待这类耗时操作。日志里频繁的 CFPrefs 读取很可疑。
3. **和蓝牙有关**：如果有一段「蓝牙设备连上 / 断开 → 改变拦截状态」的逻辑，就查断开重连之后状态有没有恢复。

## 复现思路
- 让它长时间运行（超过 1 天），中间经历：蓝牙键盘休眠再唤醒、VNC 远程连入、切换输入法、系统长时间不碰。
- 加一个日志：回调每次**没有**放行事件时，打一行日志，写清楚原因和当前状态。下次再出问题，看日志就能直接定位。
- 加一个保险：如果连续 N 秒所有按键都被吞（或者检测到用户在狂按），就自动关掉拦截器并放行。

## 排查结论（2026-11-10 下午，对照代码与系统日志）

### 证实了的
- **按键是在 vInput 的事件 tap 那一层丢的。** Siri 的热键监听位于 HID 层、在我们 tap 的上游（它看得到被我们吞掉的 F5）。事故期间它照样收到了 K580 的按键（10:32:38、10:33:25）和 VNC 的按键（10:37–10:39，修饰位带 `0x20000000`）。而 WindowServer 的键盘焦点记录显示，10:31:18 之后焦点一直在终端。上游有、焦点对、终端没收到，中间只隔着 vInput 那两个常开、能拦截（`.defaultTap`）的会话层 tap；退出 vInput 立刻恢复。
- **从 10:30:50 起，按键抑制器的回调再也没见过遥控器的 F5。** 之前 122 次遥控器会话，每次都有 `会话期间按键 keyCode=96`；session 123–125 一行都没有。同一时刻 Siri 照样收到了 F5。
- **「每次输入都读偏好设置」这条推断不成立。** vInput 主线程的 `Loading Preferences From User CFPrefsD` 与 WindowServer 切换键盘焦点的时刻逐秒对得上，是 `ModalPanels` 监听「前台应用切换」触发的，跟按键无关，也不在 tap 回调里。
- 两个 tap 回调的每个分支都放行事件；收到 `tapDisabledByTimeout/UserInput` 时也都会重新启用。代码里没有能「吞掉所有键」的分支。
- 主线程没卡死：10:40:51 的退出 AppleEvent 是在主线程上处理的。

### 没查实的
- **回调为什么不再被调用。** 主线程活着，代码也不会吞全部键；现有日志给不出直接证据。

## 修复：tap 卡死看门狗（`Sources/vInput/Remote/TapStallGuard.swift`）

不赌根因，赌结果：拦截型 tap 一旦收不到事件，最坏后果是吞掉整台机器的键盘，而这件事**可以从外面量出来**。

- 每 0.5 秒用 `CGEventSource.secondsSinceLastEventType(.combinedSessionState, .keyDown)` 问系统「最近一次按键是什么时候」。这个读数不经过我们的 tap。拿它和「我们的回调最近一次见到按下沿的时刻」对账。
- 系统有、我们超过 2 秒还没对上，就判定卡死：**先拆掉 tap（键盘立刻回来）**，再重建一个新的。
- 5 分钟内最多重建 3 次，超了就只拆不建，**键盘优先**；遥控器整个停掉再启动（`stop()`）才清账。
- 安全输入（密码框）开着时不判，因为那时 tap 本来就收不到按键。
- 两个 tap（按键抑制器、回声吞键器）都挂上了。
- 新增日志：`…卡死：…已拆掉重建`、`…卡死：…不再重建`、`…被系统停用（回调超时/用户输入），已重新启用`。以前被系统停用时是静默的。

### 验证
- 单测 1557 条 / 184 套件全绿（新增 14 条）。13 条变异全部杀死，包括「卡死后不拆旧 tap」「放弃后照样装回去」「安全输入时也判」「预算差一」等。
- 真机：新包启动后两个 tap 都装上了；注入 5 次 F19，零误判。
- 端到端：用真 `TapStallGuard`（`.system` 环境、真计时器、真系统读数）加一个只监听的真 tap。健康阶段注入 4 次 F19，零误判；停用 tap 后注入 1 次，**2.5 秒后判定卡死**。
- **没验证的**：事故本身没法复现，所以「真卡死时拆掉 tap 能不能救回键盘」只有推理（WindowServer 移除 tap 后不再等它，与「退出 vInput 立刻恢复」同理），没有实测。

### 下次再出事看什么
`grep -E "卡死|被系统停用" ~/Library/Logs/vInput/vInput.log`。
- 有 `卡死…已拆掉重建`：看门狗生效了，记下时间，往前翻当时在做什么。
- 什么都没有、键盘却又被吞：说明看门狗的前提（系统读数会更新）不成立，要换思路。先用 `log show --predicate 'process == "Siri" AND eventMessage CONTAINS "HotKey: event modifiers"'` 确认按键有没有进系统。
