# M8 设计：多语种输出（翻译）

- 日期：2026-08-18
- 状态：已与用户确认
- 前置：M7 已合并（main 218 提交，762 测试全绿）

---

## 一、范围

**M8 只做翻译。** 原 M8 装着三样东西——场景风格 profile、润色、多语种输出
——它们共用同一套机器（把转写文本重写一遍、都过不了拼音闸门、都需要更强的
模型），所以放在一起设计是对的，但工作量够两三个里程碑。

**先做翻译，因为它是三个里唯一有机器可验闸门的**：译文里出现汉字就是错的，
一行代码能判。这与 M4 拼音闸门的地位相同——有闸门就能先跑起来，
不必先解决「怎么保证不改变原意」这个更难的问题。

润色与场景 profile 顺延。

### 范围内

| | |
|---|---|
| 目标语言 | 英 / 西 / 德 / 葡 / 法 / 意（**拉丁字母**） |
| 触发 | 菜单栏「输出语言」全局开关 |
| 失败处理 | 注入中文原文 + HUD 标注 |
| 后端 | 本地优先；云端可插拔且**默认关** |

### 范围外，及理由

**日语、韩语顺延——不是技术做不到，是没有判断质量的手段。**

两个后果决定了这条：

1. **「译文里不该有汉字」这个闸门对日语完全失效**——日文本来就用汉字。
   韩语不用汉字，但字符集判定不如拉丁字母干净。
2. **日韩两种语言用户与实现方都读不了。** M5 建的基准集是中文参考文本，
   翻译这件事上一条参考译文都没有。模型输出一段看起来像日语的东西，
   我们无从判断它是不是把「报价三百」翻成了「报价三千」——
   **而这个工具会把文字直接注进用户即将发出的窗口**。

拉丁字母语种则相反：混语、漏译、残留汉字**肉眼可见**，闸门也有效。

日韩要做，得先有判据手段（回译校验是候选，代价是延迟翻倍）。

## 二、第 0 步：先测量，不写实现代码

**本地路线目前没有依据。** 2026-08-17 实测 `qwen2.5-7b-instruct-4bit`：

| | 结果 |
|---|---|
| 中 → 英 | 三条全部可用，1.7–3.3 秒。报价那条数字一个没错，MOQ、电汇预付等术语地道 |
| 中 → 西 | **三条里两条不能用**——一条混进英文单词 `still`，一条说了半句退回中文 |

德 / 葡 / 法 / 意**一条都没测过**。

**订正一处此前的错误说法**：那次实测用的是 Qwen（MLX），**不是 Whisper
Turbo**。Whisper 的 `task: .translate` 是模型内置能力，把音频直接译成英文、
不经过中文文本，是完全不同的路径，**至今完全没测过**，且只能译成英语
（`vendor/WhisperKit/.../Configurations.swift:135` 写死 X→English）。

### 要测什么

| 对象 | 目的 |
|---|---|
| Qwen 7B / 8B / 14B × 六语种 | 本地是否可行；哪个尺寸够用 |
| prompt 优化能否救回西语 | M5 证明过 prompt 能决定成败（turbo 靠换 prompt 反超 large-v3） |
| Whisper `task: .translate` 的英语质量 | 决定要不要加英语快路子（方案 B，见第三节） |

### 怎么测——复用 M5 基准集，加翻译专用指标

素材用现成的 23 条真人录音，标准文本已知，因此下列全部可机器判：

| 指标 | 判据 |
|---|---|
| **残留汉字数** | 应为 0。这是最硬的一条 |
| **技术术语原样保留** | `Azure`、`useMemo`、`GitHub Actions` 译过去不该变形。复用 `BenchMetrics.technicalTerms` |
| **数字保留** | 报价那条：「十二美元五角」→ `$12.50`。数字译错是最贵的错 |
| **长度比** | 译文/原文字符比。漏译会明显偏短 |

拉丁字母语种还可人工抽查——用户能读英语，其余语种至少能看出混语与残留。

### 这一步的产出决定后面的路

**测不出可用的本地方案，就回头重新定「云端默认关」这条决定**——
那时的理由是「本地做不到」，与「懒得做本地」是不同性质的决定，
值得重新过一遍。

## 三、架构

### 选定：方案 A —— 转写后翻译，本地优先

```
Whisper 出中文 → 本地 LLM 译成目标语言 → 闸门检查 → 注入
                                          ↓ 不过
                                   注入中文原文 + HUD 标注
```

### 排除的两条

**方案 B：英语走 Whisper 原生 `task: .translate`，其余走 LLM。**

排除的决定性理由是**中文原文必须一直在手上**：用户选定的失败处理是
「注入中文原文 + HUD 标注」，而 Whisper 直接把音频变成英文，
**中间根本没有中文文本**——译砸了连退路都没有，闸门也失去参照。

次要理由：两套行为要维护；Whisper translate 的质量完全没测过。

**英语快路子可以以后再加，但要先有数据证明它值这个代价**（第 0 步会测）。

**方案 C：云端优先。** 与 2026-08-18 已定的「云端默认关、用户显式开」
直接冲突，不再讨论。

### 组件（照抄 M4 校正层的结构）

```
TranslationPipeline   纯逻辑：超时、闸门、退回原文        ← 可测
   ↓ Translator 协议
MLXTranslator         本地实现                          ← 脏
GeminiTranslator      云端实现，默认不加载               ← 脏
```

M4 的对应物是 `CorrectionPipeline`（纯）/ `Corrector`（协议）/
`MLXCorrector`（脏）。**照抄这个结构，不用另行设计**——它在 M4 验证过，
而且纯逻辑那一半天然可移植（见 Roadmap 的 Windows 一节：42/69 个源文件
只依赖 Foundation，而这是被 TCC 逼出来的可测性带来的意外收获）。

`TranslationGate` 独立且纯，与 `CorrectionGate` 地位相同——
**它是这一层唯一的机械保障**。

### 组件清单

| 文件 | 职责 | 纯度 |
|---|---|---|
| `TranslationTarget` | 支持的目标语言枚举 + 语言名 / prompt 用的英文名 | 纯 |
| `TranslationGate` | 译文的机械检查（见第五节） | 纯 |
| `TranslationPipeline` | 编排：超时、调用闸门、失败退回 | 纯 + 注入 |
| `Translator` | 协议：`translate(_:to:) async throws -> String` | 协议 |
| `MLXTranslator` | 本地实现，复用 `OneShotLoader` | 脏 |
| `GeminiTranslator` | 云端实现，key 从 Keychain 读 | 脏 |
| `TranslationPreference` | 输出语言、云端开关、模型目录，跨启动保留（照 `CorrectionPreference`） | 纯 |

## 四、数据流，及两处与现有代码的交互

```
音频 → Whisper（中文）
    → 校正层（M4）              ← 必须在翻译之前
    → 输出语言 == 中文？ 是 → 注入
                         否 → TranslationPipeline
                               ↓ 闸门过        ↓ 不过
                             注入译文     注入中文原文 + HUD 标注
```

### ① 校正必须在翻译之前

带同音错字的中文译过去，错误会被**固化**：用户说「上线」而转写成「上限」，
译过去就是 `upper limit`——**译文里看不出这是个同音错字**，而中文原文里
校正层本来能修掉它。

代价：开翻译时校正也得开着，两段推理的延迟叠加。用户已确认接受。

### ② 全角标点转换不影响译文——查过，是我先前判断错了

设计评审时我写过「`normalizePunctuation` 是无条件跑的，英文译文里会出现
『，』，要按输出语言分流」。**核实后不成立**：

```
Sources/vInput/Transcribe/WhisperKitTranscriber.swift:572
    let cleaned = TranscriptCleaner.clean(raw)      ← 唯一调用点
```

`clean()` 只作用于 Whisper 的输出（中文），而翻译在下游（校正之后、
注入之前）。**译文根本不经过 `normalizePunctuation`。**

写在这里是为了让它是「查过、没问题」而不是「没查」——
免得以后有人照着这条去修一个不存在的问题。

**因此本设计不需要改动既有转写层代码。**

### ③ 翻译插在哪一环

`DictationSession.finish()` 里，校正与注入之间：

```swift
transition(to: .correcting)   // 已有
...
transition(to: .translating)  // 新增
...
transition(to: .injecting)    // 已有
```

新增一个 `.translating` 状态。HUD 与菜单栏的粗粒度状态（`Phase.working`）
不必区分到这一级——与 `.correcting` 同样处理。

## 五、闸门：`TranslationGate`

拉丁字母目标语言下的机械检查。**任一条不过即判定失败**，走退回路径。

| 检查 | 理由 |
|---|---|
| **残留汉字** | 最硬的一条。译文里出现汉字＝没译完或退回了中文 |
| **中文标点残留** | 「，」「。」「？」出现在拉丁字母译文里同样是失败信号 |
| **长度比下限** | 译文过短说明漏译。阈值由第 0 步的数据定，不拍脑袋 |

**故意不做的检查**：语义正确性。那需要另一个模型，而「用更强的模型检查
更强的模型」是无穷回退。闸门只保证「明显错了的挡下来」，
不保证「过了的就是对的」——与 `CorrectionGate` 同一个定位。

**测量指标（第 0 步用）与闸门（生产用）共用判据函数，但度量点在转换之前。**
这是 M6 的教训：`BenchMetrics.halfWidthPunctuationInChinese` 最初与转换器
共用同一个函数又跑在转换之后，成了恒等式，指标必然读 0。

## 六、失败处理

复用 M6 建立的规矩——**不静默失效**：

| 情形 | 行为 |
|---|---|
| 推理超时 | 注入中文原文 + HUD 标注 |
| 模型未就绪（加载中） | 同上，HUD 区分「加载中」（可以等） |
| 闸门不过 | 注入中文原文 + HUD，**日志记具体哪条不过** |
| 选了云端但没配 key | **禁用云端后端并在 HUD 提示**，不静默退回本地 |

最后一条是 M6 ③ 的直接教训：一个「静默不工作」的功能，
用户看到的只有「没变化」，无从判断是哪一种。

## 七、测试

| 层 | 做法 |
|---|---|
| `TranslationGate` | 纯函数，重点覆盖：六种语言 × 残留汉字 / 中文标点 / 长度不足 |
| `TranslationPipeline` | 注入假 `Translator`，测超时、退回、闸门各条路径 |
| 真模型 | 门控 E2E，照 `CorrectionE2ETests` 的标记文件做法 |
| 度量 | 扩展 `scripts/bench-run.sh`，加翻译那几格 |

**`MLXTranslator` / `GeminiTranslator` 本身进不了单元测试**——前者要加载
2 GB 模型，后者要网络。这与 `MLXCorrector` 同样处理：协议隔开，
纯逻辑全测，脏实现走门控 E2E。

## 八、两处故意留到测量之后

**延迟预算。** M4 校正是 8 秒，那个数是真机实测定的（6/9 次会话在 3 秒
预算下超时）。翻译是两段推理，但用户选了全局开关——说明他在「写英文」
模式里，延迟预期本来就不同。**测出真实耗时再定，不拍脑袋。**

**默认后端。** 本地 vs 云端取决于第 0 步的结果。

## 九、验收标准

1. 菜单栏能切换输出语言，状态跨启动保留
2. 选定拉丁字母语种后，说中文出该语言文字，注入光标处
3. 闸门拦下时注入中文原文且 HUD 有标注，日志记明原因
4. 云端后端默认不加载；显式开启且未配 key 时 HUD 明确提示
5. 基准集能跑出翻译那几格指标，一条命令、无人值守
6. 会话状态多出 `.translating`，且校正在翻译之前（同音错字不被固化）
