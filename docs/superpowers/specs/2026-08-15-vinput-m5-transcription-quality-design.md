# M5 设计：转写质量优化

- 日期：2026-08-15
- 里程碑：M5
- 许可：GPL-3.0-only

## 一、这是什么

**用一套真人语音基准集，把转写质量的改进从「感觉好像好一点」变成可量化、
可回归的工程。**

M5 不做新功能，做的是**度量能力**与基于度量的调优。

## 二、为什么改变了原定路线

原始设计（`2026-08-11-vinput-design.md`）的 M5 是「场景风格」——三个 profile
按前台应用切换润色风格。**本设计把它顺延到 M6**，M5 改做转写质量。

### 依据：M4 收尾时的真机数据

用户读六段标准文本（正确答案已知），错误归因：

| 用户说的 | 转写出来的 | 错在哪层 | 下游能修吗 |
|---|---|---|---|
| 代码**里**有个问题 | 代码有个问题 | 转写漏字 | ❌ |
| 上**线**计划 | 上**限**计划 | 转写（同音） | ✅ |
| 会议室见**面** | 会议室见 | 转写漏字 | ❌ |
| **比如**说 | **比方**说 | 转写换词 | ❌ |
| **Claude Code** | **collodecode** | 转写听错 | ❌ |
| **GitHub Actions** | github actions | 转写丢大小写 | ❌ |
| 权限**配置** | 权限 | 转写漏字 | ❌ |

**七个错误里只有一个是下游能修的。**

根本原因：**下游看不到音频。** Whisper 一旦写出「collodecode」，声学证据就没
了，任何 LLM 都只能靠上下文猜——而「不许猜」正是 M4 拼音闸门存在的全部意义。
漏字更彻底：字压根没进入文本，下游连「这里少了东西」都不知道。

**在转写层不够好的时候做润色，等于在一段已经错了的文字上精修排版。**

### 依据：改善收益的悬殊对比

| 改动 | 层 | 效果 |
|---|---|---|
| 加 initial prompt（标点） | 转写 | 24 秒长文标点 **0 → 7** |
| 加 initial prompt（技术专名） | 转写 | `Claude Code`/`GitHub Actions`/`AWS` **1/3 → 3/3** |
| 校正层六轮提示词迭代 | 校正 | 六段测试**修对 1 次** |

转写层两次小改动的收益，远超校正层六轮迭代。

### 场景润色顺延到 M6 的另一重理由

用户提出：**本地模型可能根本做不了润色，需要云端模型。**

这个担心有数据支撑。Qwen3-4B 连「只改同音错字」这个更简单的任务都吃力
（六段测试修对 1 次，还输出过推理过程、把正确词当错误）。而润色是**带风格
约束的语义改写**，难度高一个量级。

更要紧的是安全网：校正有拼音闸门（同音才准改，机器可验证），**润色天然要
改读音，闸门用不上**。能力更弱的模型配更弱的安全网，是个危险组合。

因此 M6 规划时应重新评估原始设计里那条「可插拔，默认本地，云端可选」。
M4 选了只做本地——对校正是对的（有闸门兜着），对润色可能不成立。

## 三、基准集

### 结构

```
Bench/
├── manifest.json          ← 进版本库
└── audio/                 ← 不进版本库
    ├── tech-01.wav
    └── ...
```

`manifest.json` 记录每段的文件名、标准文本、类别。**它进版本库**，基准集的
定义因此可复现、可追溯、可 review。

`audio/` **不进版本库**：二进制且是用户的声音，写进 git 历史不可撤销。
它位于 OneDrive 同步目录内，因此有云端备份，不怕本机丢失。

### 关于「音频不落盘」

原始设计的隐私一节写明「音频不落盘，仅存在于会话期间的内存缓冲中」。

**基准集是这条原则的一个明确例外，范围严格限定**：

- 只有专门的录制工具会写音频，**听写主路径一行代码不改**——日常使用仍然
  音频不落盘
- 录音只存在本机（含 OneDrive 同步），不进版本库
- 该例外仅为开发期度量而设，不随应用分发

### 内容

四个类别，各 5–8 段，共 20–30 段：

| 类别 | 考察 | 例 |
|---|---|---|
| 技术术语与代码标识符 | 用户主场景，也是当前错得最惨的一类 | `useEffect`、`Claude Code`、`GitHub Actions`、`AWS` |
| 长句与标点 | 连说 15–30 秒不停顿，测断句与标点密度 | 需守住 initial prompt 已取得的改善 |
| 同音陷阱 | 直接考验校正层，也是判断「换模型/改 prompt 有没有用」的主依据 | 写代码/鞋代码、句子/矩子、上线/上限 |
| 口语与日常表达 | 验证「不该改的不要改」（负例），也为将来的口语 profile 备着 | 带口水词、不完整句、重复 |

标准文本由实现者编写，**必须包含 M4 期间真机出现过的实际错误**
（`鞋代码`、`矩子`、`上限`、`collodecode`），它们是已知会失败的样本，
比编造的更有价值。

## 四、度量

三层，缺一不可：

| 层次 | 指标 | 用途 |
|---|---|---|
| 总体 | **字错误率（CER）**：编辑距离 / 参考文本长度 | 一个数看全局，防整体回归 |
| 分类 | 技术词命中率、标点数、同音陷阱命中率、负例改动数 | 定位改动影响了哪一类 |
| 逐段 | 标准文本与实际输出的 diff | 出问题时看得见具体错在哪 |

**分类指标不能被总体指标取代。** 一次改动可能让 CER 微降却把技术词全毁掉——
今天就出现过类似情形：某个 prompt 变体在多数音频上标点持平，却把两段的标点
砍掉一半。只看一个数会漏掉。

**负例改动数是硬约束**：口语类的标准文本本来就是对的，被改动就是回归，
无论 CER 多好看。

## 五、工具

两个开发期工具，不进主应用，不随分发：

### 录制工具

按 manifest 逐条提示、录音、存盘，可重录单条。

用户录一次约半小时，之后长期复用。**必须能重录单条**——一次性录完 30 段
不允许出错是不现实的。

**必须解决麦克风权限**。macOS 的 TCC 授权绑定应用 bundle，纯命令行工具拿不到
麦克风——现有的 `vInputBench` 是读预录音频文件，没有先例可循。三条可选路径，
实施时择一并说明理由：

1. 做进主应用（菜单栏加一个「录制基准集」入口）——复用已有的麦克风授权与
   `SystemMicSource`，代价是开发期工具混进了产品代码
2. 单独打一个最小 `.app`——干净隔离，代价是要单独授权、单独维护打包脚本
3. 复用主应用的听写路径，把音频落盘作为一个仅在特定环境变量下开启的分支
   ——代价是碰了「主路径不落盘」这条线，**与本设计第三节的约定冲突，不推荐**

第 1 条最省事，第 2 条最干净。这个选择要在实施计划里定下来，不要留到编码时
临时决定。

### 对照工具

一键跑全集，输出三层指标与 diff 报告。支持：

- 指定 Whisper 模型（做 large-v3 vs turbo 这类对照）
- 指定 `DecodingOptions` 参数
- 指定是否启用校正层
- 两次运行的结果对比（before/after）

**它必须能在无人值守下跑完**——这正是建基准集要解决的问题：此前每轮变更都
要拉用户读一遍，迭代速度受限于用户的时间。

## 六、有了基准集之后要测的

按预期收益排序，**本设计不预设结论**：

1. **large-v3 vs turbo** —— 模型已在 `vendor/models` 本地，成本最低。用户当初
   选 turbo 的前提是「延迟只有一两秒」，而现在链路上校正已占数秒，多出的转写
   时间占比完全不同
2. **`DecodingOptions` 调参** —— 温度回退策略、beam search、`patience`
3. **initial prompt 继续迭代** —— 已见效（标点 0→7、技术词 1/3→3/3），仍有余量
4. **`docs/M5-Backlog.md` 里的体验缺口** —— 注入延迟、HUD「本次未校正」标注、
   换模型时重复加载

## 七、不做

- **场景风格与润色层** —— 顺延到 M6，理由见第二节
- **改动听写主路径的音频处理** —— 基准集的录音由独立工具完成，主路径仍然
  音频不落盘
- **把基准集音频进版本库或随应用分发**
- **换校正模型** —— M4 已实测 Qwen2.5-7B 更差且慢 3–4 倍，容量不是瓶颈
  （见 `docs/M5-Backlog.md` 第六节）

## 八、验收标准

**任意一项转写层改动，都能在一条命令内得到量化的前后对比，无需用户参与。**

具体地：

1. 基准集录制完成，20–30 段覆盖四个类别
2. 对照工具能跑完全集并输出三层指标
3. 用它完成至少一次真实对照（large-v3 vs turbo），并据此做出模型选择的决定
4. 负例类别的改动数为 0
