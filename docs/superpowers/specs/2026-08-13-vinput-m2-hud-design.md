# vInput M2 设计：HUD 与实时预览

- 日期：2026-08-13
- 状态：已确认，待编写实施计划
- 上位文档：[M1 总体设计](2026-08-11-vinput-design.md)

## 一、目标

说话时能在浮窗里看到文字逐渐出现，同时能看到录音状态、时长与音量。

**实时预览是本里程碑的既定目标，不再讨论取舍。**

## 二、M1 之后前提的变化

M1 原设计中，实时预览的理由是「最终文本要等 0.5–2 秒才到，需要中间反馈」。M1 把默认模型定为 `turbo` 后，实测等待远低于当初估计：

| 场景 | 音频 | 松手后等待 |
|---|---|---|
| 闲聊 | 4.0 s | 0.60 s |
| 技术短句 | 5.1 s | 0.71 s |
| 技术密集 | 12.1 s | 1.09 s |
| 长文 | 24.6 s | 1.58 s |

即「等待焦虑」这一原始理由已大幅削弱。该情况已向用户说明，用户确认实时预览仍是既定目标。因此本设计不再以「减少等待感」为依据，而以「说话过程中的可见反馈」本身为目标。

一个仍然成立的推论：若用户切回 `large-v3`（长文 24.6 s 需等 8.71 s），预览的价值会显著回升。

### 已决：默认模型保持 `turbo`（2026-08-14 实测后确定）

M2 实现实时预览后，用户在真机上对两个模型各跑了一遍长文，结论是
**`large-v3` 可用但整体体验不好，默认保持 `turbo`**。

即：实时预览确实削弱了等待的成本，但**没有削弱到足以抵消 `large-v3`
慢 3–5.5 倍**的程度。下面推演中「预览可能让 8.7 秒变得可接受」这一假设
未被实测支持。

`large-v3` 仍留在偏好列表中，可从菜单栏随时切换——需要质量天花板的场合
（如长文定稿）仍然用得上。

以下是当初推迟决定时的推演，保留以说明判断依据：

---

**默认模型用 `turbo` 还是 `large-v3`，推迟到 M2 实现并实测之后再定。**

理由是二者互相影响，现在决定缺少依据：

- **实时预览会削弱「等待」的成本。** 松手前文字已经在 HUD 上出现过，用户知道自己说了什么、系统听对了没有。此时再等几秒拿更准的最终结果，主观感受与「盯着空白等」完全不同。这可能让 `large-v3` 长文 8.71 s 的等待从「难以忍受」变成「可以接受」。
- **反过来，预览本身要消耗算力。** 用 `large-v3` 时预览的增量转写也更慢，可能跟不上说话速度而触发第七节的降级（落后 3 秒即暂停文本更新）。若如此，`large-v3` + 预览的组合就不成立。

因此 M2 验收时需实测两件事，再做决定：

1. `large-v3` 下预览能否跟上实时（是否频繁触发降级）
2. 有了预览之后，`large-v3` 的最终等待主观上是否可接受

在此之前默认保持 `turbo`（M1 的决定），菜单栏可随时切换，不阻塞任何工作。

## 三、范围

### 做

- 无焦点浮动 HUD：录音状态、时长、音量波形、实时文本
- 基于 WhisperKit `AudioStreamTranscriber` 的流式预览
- 已确认 / 未确认文本的视觉区分
- `Esc` 取消当前会话

### 不做

- HUD 的鼠标交互（与不抢焦点的硬约束冲突）
- 预览文本的润色（M4）
- HUD 位置自定义（M6 设置界面）
- 流式结果直接注入（见本节「已定的关键决策」）

### 已定的关键决策

**最终注入的文本仍走全量转写，流式仅用于预览。**

流式转写分块处理，缺少全局上下文，质量低于一次性全量转写。M1 已验收的质量不应为零等待让步。预览文本在注入前被最终结果整段替换，从不进入目标应用。

## 四、架构

### 数据流

音频在 `AudioSource` 之后分叉，喂给两个互不知情的消费者：

```
                    AudioSource（麦克风 / M3 蓝牙）
                            │ [Float] @16 kHz
                ┌───────────┴───────────┐
                ↓                       ↓
        AudioBuffer                SourceBackedAudioProcessor
        （累积全量音频）              （实现 WhisperKit 的
                │                      AudioProcessing 协议）
                │                       ↓
                │                AudioStreamTranscriber
                │                （WhisperKit 自带：增量转写、
                │                  窗口切分、已确认/未确认区分）
                │                       ↓
                │                  预览文本 + 音量数据
                │                       ↓
                │                     HUD
                ↓
        松手 → 全量转写 → 注入光标
```

**分叉点在 `AudioSource` 之后**，因此 M3 接入蓝牙遥控器时，流式预览零成本自动可用——蓝牙源只需实现同一个 `AudioSource` 协议，两条支路均无需改动。

### 为什么复用 WhisperKit 的流式引擎

流式转写的难点不是定时调用，而是**窗口边界的文本拼接与去重**，以及判断哪部分文本已稳定、哪部分后文仍会修正。`AudioStreamTranscriber` 已实现该逻辑，并暴露：

```swift
public var bufferEnergy: [Float]                       // 音量条数据
public var currentText: String                         // 当前文本
public var confirmedSegments: [TranscriptionSegment]   // 已确认，不再变
public var unconfirmedSegments: [TranscriptionSegment] // 未确认，可能被改写
```

自行实现这段逻辑大概率会在中文分词边界上出问题。

### 为什么需要适配层

`AudioStreamTranscriber` 接受 `audioProcessor: any AudioProcessing` 协议，通过 `startRecordingLive` / `audioSamples` / `relativeEnergy` 三个入口取音频，**不自己开麦克风**。这正是所需的接缝。

`AudioProcessor` 虽为 `open class`，但其方法均为 `public` 而非 `open`，**跨模块无法重写**，因此不能通过继承注入。必须自行实现 `AudioProcessing` 协议。

`SourceBackedAudioProcessor`（约 120 行）职责：

| 职责 | 说明 |
|---|---|
| 接收 `AudioSource` 推来的帧 | 追加到 `audioSamples` |
| 计算相对能量 | HUD 音量条的数据来源，逐块 RMS 后归一化 |
| 生命周期方法 | `start/stop/pause/resume` 近乎空操作——音频由 `AudioSource` 驱动 |
| 静态工具方法 | 转发给 `AudioProcessor` 的现成实现 |

### 计算开销

`AudioStreamTranscriber` 是增量的：每次只转写 `lastBufferSize` 之后的新音频，并从上次确认点继续，不重转全部。预览总开销约等于一次完整转写，摊在说话过程中，不叠加到松手后的等待上。

松手时**先停流式、再跑全量**，避免两者争抢神经引擎。

## 五、HUD

### 窗口性质

`NSPanel` + `.nonactivatingPanel` + `.floating` 层级，**不抢焦点**。

这是硬约束：用户在别的应用里说话，焦点必须始终留在目标输入框上，否则文字无处可注。

直接后果：**HUD 上不能有任何需要点击的控件**，所有操作只能靠键盘。

### 位置

**屏幕底部居中，距底边约 120 px。**

位置固定可预期，不遮挡工作区，与 macOS 自带听写的位置一致。不依赖辅助功能 API 查询光标位置——终端、Electron 及部分 Web 输入框根本不暴露该信息。

### 布局

```
┌──────────────────────────────────────────────┐
│  ●  0:07   ▁▃▅▇▅▃▁▂▄▆▄▂▁▃▅                  │
│                                              │
│  帮我把这个函数里的依赖数组改一下，              │
│  然后跑一遍测试                                │
│                                              │
│  ⌥D 完成    Esc 取消                          │
└──────────────────────────────────────────────┘
```

| 区域 | 内容 | 解决的问题 |
|---|---|---|
| 状态点 | 录音中（红）/ 转写中（转圈）/ 出错（黄） | 它到底在不在工作 |
| 时长 | `0:07` | M3 的遥控器有 60 秒硬限制，需要看到逼近 |
| 音量波形 | 实时能量条 | 麦克风有没有收到声音——看不见任何东西时最真实的焦虑 |
| 文本 | 已确认 + 未确认 | 实时预览本体 |

### 已确认与未确认的视觉区分

- **已确认**：正常颜色，不会再变
- **未确认**：半透明灰，后文可能改写

缺少该区分时，文本会时不时整段跳变，观感如同故障。

### 键位语义

| 键 | 行为 |
|---|---|
| `⌥D` | 正常结束：全量转写 → 注入光标 |
| `Esc` | 取消：丢弃音频，不注入 |

`Esc` 用 Carbon 全局热键注册，**仅在录音期间注册，结束立即注销**。影响范围限于录音的那几秒，且用户此时在说话而非打字。

### 生命周期

会话开始时淡入，注入完成或取消后淡出。空闲时窗口不存在。

### 更新节流

| 数据 | 频率 | 原因 |
|---|---|---|
| 音量波形 | 20 fps | 音频回调约每 0.1 秒一次，全量重绘浪费 |
| 文本 | 事件驱动 | 流式转写约 1–2 秒产出一次 |
| 时长 | 10 fps | 只需显示到秒 |

长时间说话时文本会超出面板高度：**文本区固定为 4 行高，超出后只显示末尾 4 行并跟随最新**，不做滚动条（HUD 不可交互）。

## 六、`DictationSession` 的改动

状态机保持不变，仅增加预览支路与一个新的终止方式：

```
idle ──start()──→ listening ──finish()──→ transcribing → injecting → idle
                      │                                              ↑
                      └──────────────cancel()────────────────────────┘
```

新增三项：

| 新增 | 说明 |
|---|---|
| `previewEngine: PreviewEngine?` | 新 protocol，可注入。有了它才能在不加载真实模型的情况下测试预览生命周期 |
| `onPreview: ((PreviewText) -> Void)?` | 向 HUD 推送已确认/未确认文本与能量数据 |
| `cancel()` | 丢弃音频，不注入，直接回 idle |

`PreviewEngine` 是新的接缝，与现有三个 protocol（`AudioSource` / `Transcriber` / `TextSink`）平级。

推送给 HUD 的数据结构：

```swift
struct PreviewText: Equatable {
    /// 已确认的文本，不会再被改写。
    let confirmed: String
    /// 未确认的文本，后续可能被修正。
    let unconfirmed: String
    /// 归一化到 0…1 的最近能量值，供音量波形使用。
    let energy: [Float]
}
```

### `cancel()` 的语义

丢弃音频、不注入、回到 idle，并**显式清空 `retainedSamples`**。

取消是用户主动放弃，不该留存；而转写失败保留音频是为了重试。两者语义不同，不可混淆。

## 七、错误处理：规则二在新层的延伸

预览是锦上添花，主路径是不能丢字。**任何预览侧的故障，都不得让用户说的话丢失。**

| 失败 | 处理 |
|---|---|
| 流式转写报错 | 记日志、关闭预览、**录音继续**。HUD 文本区显示「预览不可用」，时长与音量条照常，松手后全量转写照常执行 |
| 流式引擎启动失败 | 同上——录音正常开始，只是没有预览 |
| 预览与全量争抢神经引擎 | 松手时先停流式再跑全量，并丢弃在途的预览结果 |
| 长时间录音预览积压 | 预览落后实时**超过 3 秒**时自动降级：停止更新文本，仅保留音量与时长。HUD 文本区显示「预览已暂停」 |

## 八、测试策略

| 层 | 方式 |
|---|---|
| 相对能量计算 | 纯函数，给定波形断言输出范围与归一化，单元测试 |
| `DictationSession` 的预览生命周期 | 注入 `FakePreviewEngine`：验证 start 时启动、finish 时**先停预览再转写**、cancel 时全部停止且不注入 |
| **预览失败不影响主路径** | **测试重点。** 让 `FakePreviewEngine` 在各时机报错，断言全量转写与注入仍正常完成 |
| `cancel()` | 验证不注入、清空保留音频、回到 idle |
| HUD 视图逻辑 | 时长格式化、已确认/未确认拆分、文本截断，纯函数单元测试 |
| `NSPanel` 不抢焦点 | 无法自动化。真机手测：在备忘录里说话，确认光标仍在闪烁、文字仍能注入 |
| 流式转写质量 | 不做断言，用 `scripts/bench.sh` 人工对比 |

## 九、验收标准

在备忘录中按 `⌥D` 说一段话：

1. 屏幕底部出现 HUD，显示红色状态点与递增的时长
2. 音量波形随说话起伏
3. 文本在说话过程中逐渐出现，已确认部分颜色正常、未确认部分为灰色
4. 按 `⌥D` 结束后，HUD 淡出，最终文本注入光标处
5. 重复一次，中途按 `Esc`：HUD 淡出，**没有任何文字被注入**
6. 全程目标应用的光标保持闪烁（HUD 未抢焦点）
