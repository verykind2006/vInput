# M4 设计：本地 LLM 校正层

- 日期：2026-08-14
- 里程碑：M4
- 许可：GPL-3.0-only

## 一、这是什么

在转写与注入之间插入一层，**修正 Whisper 听错的字词，不改变说话人的措辞**。

真机触发这个里程碑的具体案例：用户说「小米遥控器」，`large-v3-turbo` 输出「小米耀空气」。
这是同音词错误（yáo kòng qì / yào kōng qì），纯声学解码无法自行纠正——修正它需要
「小米后面跟遥控器」这样的常识，那是语言模型的领域，不是声学模型的。

## 二、职责边界

**只改错字，不改措辞。**

| 该修 | 不该碰 |
|---|---|
| 耀空气 → 遥控器 | 语序、句式 |
| 副作用钩子 → useEffect | 标点风格、口水词 |
| 数据裤 → 数据库 | 书面化程度 |

原始设计（`2026-08-11-vinput-design.md`）把 M4 定为「润色层」，涵盖标点、口水词、
书面化。**本设计将其收窄为「校正」，把润色并入 M5。**

理由：润色的正确答案依赖场景——同一句话在 Cursor 里该保留术语原文，在微信里该保留
口语感，在备忘录里该书面化。脱离场景谈「润不润色」没有确定答案，而场景风格正是 M5
的内容。拆开做两次，M4 会做出一个 M5 必须推翻的东西。

校正则不依赖场景：「耀空气」在任何应用里都是错的。因此它有清晰的验收标准——
修对了没有、有没有改坏原本对的字。

## 三、架构位置

原设计的会话状态机已预留这一格：

```
listening → transcribing → correcting → injecting
```

新增 `Corrector` protocol，与已有的 `AudioSource` / `Transcriber` / `TextSink` 并列，
是第四条接缝。`DictationSession` 只知道「有个东西可能会改文本」，不知道背后是什么。

```
┌─ 转写层  Transcriber ────────────────┐
│  large-v3-turbo 全量转写              │
└──────────────────────────────────────┘
              ↓ 原始文本
┌─ 校正层 ─────────────────────────────┐
│  Corrector      → 替换清单            │  ← 可换实现
│  CorrectionGate → 逐条过闸           │  ← 唯一一份，实现无关
└──────────────────────────────────────┘
              ↓ 最终文本
┌─ 输出层  TextSink ───────────────────┐
```

**闸门位于 `Corrector` 之外，不在任何实现内部。**

这是本设计最重要的结构决定。M4 只做本地实现，云端排在其后；若把闸门写进本地实现，
接云端时就得重写一遍——而闸门恰恰是最不该存在两份的东西：两份就会有两种松紧，
而它是唯一挡在「LLM 改写用户说的话」前面的东西。

**实时预览不走校正。** 校正需要完整句子才有上下文，对半句话做同音纠错只会添乱。
预览的定位（让用户知道系统在听）不变，校正只作用于终稿。

## 四、拼音闸门

### 输出格式

LLM **不输出整句**，只输出替换清单，一行一条，箭头分隔：

```
耀空气→遥控器
数据裤→数据库
```

选这个格式而非 JSON：4B 量级的模型产出合法 JSON 的可靠性不足，而这个格式几乎不可能
写错；即便写错，无法解析的行直接丢弃，不影响其余行。

**格式本身就是第一道保险**：模型只能逐词替换，结构上无法重写整句。

### 闸门规则

每条替换独立判定，用系统内置的 `CFStringTransform`（`kCFStringTransformMandarinLatin`）
转拼音后比对，无第三方依赖：

| 改动 | 拼音 | 判定 |
|---|---|---|
| 耀空气 → 遥控器 | yao kong qi → yao kong qi | ✅ 放行 |
| useEffect → 副作用钩子 | 读音完全不同 | ❌ 回退 |
| 那我明天再看看吧 → 明日再议 | 长度与读音均不匹配 | ❌ 回退 |

**比对忽略声调。** 同音错字绝大多数是声调差异（yào/yáo），要求声调一致会把最该修的
那一类全部拦掉。

**非汉字片段按原文精确比对。** 拉丁字母、数字不经拼音转换——`useEffect` 与
`useState` 拼音转换后都是原样，必须靠字面比对区分。

### 替换如何落到文本上

- **原文片段必须在转写中原样存在**，否则丢弃该条。模型偶尔会「引用」一个它自己
  改写过的片段，那种条目无从定位，宁可不改
- **同一片段出现多次时全部替换。** 同音错字是听错，同一个词在一句话里听错两次会
  错成同一个样子，只改第一处会留下一个不一致的句子
- **替换按原文片段长度从长到短依次应用**，避免短片段先替换后破坏长片段的匹配

### 部分采纳

**任何一条不合格只回退那一条，其余照常生效。** 不因一处可疑而丢弃全部校正——
那是把「谨慎」错用成了「浪费」。

闸门是纯函数，不依赖模型，可穷举测试。

## 五、模型与降级

### 模型

MLX Swift + Qwen3-4B-Instruct 四量化（约 2.3 GB）。

**模型目录可在运行时指定**，沿用 M1 已验证的交互：菜单栏「指定校正模型」，选一个
本地目录。

这一项在 M4 不是锦上添花而是必需：4B 在中文常识上未必够强，而「小米后面该跟遥控器」
正是常识判断。若 4B 不胜任，用户可自行换 7B/8B 试，无需等待代码改动。同一交互在
Whisper 模型上已验证可用。

### 降级路径

以下任一情形触发，**一律注入原始转写**：

| 情形 | 行为 |
|---|---|
| 模型未下载 / 加载失败 | 跳过校正，注入原文 |
| 推理超时（3 秒） | 放弃校正，注入原文 |
| 输出无法解析出任何合法替换 | 注入原文 |
| 全部替换均被闸门拦下 | 注入原文 |

校正是锦上添花，**绝不允许它的失败影响主路径**——与预览引擎在 M2 的处理方式一致。
校正失败不上报为会话错误，只记日志。

## 六、可观测性

菜单栏一个开关：**校正 开 / 关**。这就是 M4 的验收标准——同一句话开关能看出差别。

每次校正记录三项：原文、采纳的替换、被闸门拦下的替换。

这样闸门的松紧可以从日常使用的日志中判断，不需要安排专门的测试——与 M3 收尾时
`scripts/acceptance-scan.sh` 的思路一致。日志默认不记录转写内容（见原设计「隐私」
一节），校正日志沿用同一开关：用户显式开启内容级日志时才记全文，否则只记替换对。

## 七、测试策略

| 组件 | 方式 |
|---|---|
| `CorrectionGate` | 纯函数，穷举测试：同音放行、异音回退、非汉字精确比对、部分采纳、忽略声调 |
| 替换清单解析 | 畸形输入表驱动：空行、缺箭头、多箭头、原文不存在于句中 |
| 降级路径 | 四条各一个测试，断言注入的是原文 |
| `DictationSession` 接线 | 用假 Corrector，断言校正失败不影响注入 |
| 端到端 | 沿用 `PipelineE2ETests` 的门控方式（`VINPUT_E2E=1`），真实模型跑固定句子 |

**闸门与解析是纯函数，构成本里程碑的测试主体。** 模型输出本身不可断言，因此把可断言
的部分（格式解析、闸门判定、降级行为）与不可断言的部分（模型是否聪明）彻底分开。

## 八、不做

- **云端实现**——排在本地之后。接缝已留好：实现同一个 `Corrector` protocol 即可，
  闸门自动复用
- **标点、口水词、书面化**——M5
- **自定义词典 / 术语表**——先看纯 LLM 能到什么程度。过早堆砌词典会掩盖模型层面的
  真实短板
- **改动实时预览**
- **多轮校正 / 交互式确认**——用户是产品经理，明确表示不愿为每句话做审阅
