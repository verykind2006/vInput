# M5 验收清单

- 日期：2026-08-17
- 机型：Apple M3 / 16 GB / macOS 26.5.2
- 基准集：23 条真人录音（用户本人），四类覆盖

**M5 的验收标准：任意一项转写层改动，都能在一条命令内得到量化的前后对比，
无需用户参与。**

| | 标准 | 结果 |

| 1 | 基准集录制完成，23 条覆盖四个类别 | ✅ |

| 4 | ~~口语类的改动数为 0~~ | ⚠️ **标准写错了对象，见下** |

### 第 4 条的订正

原文写「口语类的改动数为 0」，本意是**校正层不该改坏本来正确的话**。
但基准集测的是**转写层**——口语类 CER 0.0093 是转写错误
（`这个事儿` → `这个事`），不是「被改坏」。

**这条标准写错了对象。** 正确的表述应当是：「口语类的 CER 不因任何转写层
改动而升高」——而这一点在九个 prompt 候选的扫描中全部满足（口语类 CER 恒为
0.0093，无一候选使其变差）。

## 二、基准集

23 条，四类：

| 类别 | 条数 | 考察 |
|---|---|---|
| 技术术语与代码标识符 | 6 | 用户主场景，M4 收尾时错得最惨的一类 |
| 长句与标点 | 5 | 连说 15–30 秒不停顿 |
| 同音陷阱 | 6 | 直接考验校正层 |
| 口语与日常表达 | 6 | 验证「不该改的不要改」 |

标准文本刻意包含 M4 真机出现过的实际错误（`写代码`→鞋代码、
`长句子`→长矩子、`上线`→上限、`Claude Code`→collodecode、
`GitHub Actions` 大小写丢失）——已知会失败的样本比编造的有价值。

录音质量核验：语速 3.1–4.6 字/秒（中文）、4.9–6.3 字/秒（含英文），
无一条偏离，说明重录覆盖机制正常、无残留的不完整片段。

**录音不进版本库**（二进制且是用户的声音），`manifest.json` 进版本库
——基准集的定义因此可复现、可 review。

## 三、当天用它得到的两个结论

### 结论一：large-v3 的优势集中在技术类，代价是 4.5 倍延迟

| | 总体 CER | technical | homophone | punctuation | colloquial | 单条耗时 |
|---|---|---|---|---|---|---|
| turbo | 0.0317 | 0.0742 | **0.0294** | 0.0105 | 0.0093 | **1.2 秒** |
| large-v3 | **0.0207** | **0.0251** | 0.0363 | 0.0105 | 0.0093 | 5.4 秒 |

large-v3 总体好 35%、技术类好 66%，**但同音类差 24%**。

**这正是「分类指标不能被总体指标取代」的实例**：只看总体 CER 会得出
「large-v3 全面更好」，而它在同音陷阱上实际更差。

用户实测 large-v3 的真机延迟：7 秒音频等 6.3 秒，反馈「有点太慢了」。

### 结论二：prompt 优化推翻了模型选择

假设：turbo 不是认不出术语，而是**只认 prompt 里点名的词**。
证据是 `tech-02`（唯一术语全对的一条）的三个词正是旧 prompt 里写着的。

扫了九个候选：

| 候选 | 总体 CER | 技术类 | 术语命中 | 泄漏 | 字数 |
|---|---|---|---|---|---|
| 旧版（只点 3 个词） | 0.0317 | 0.0742 | 0.389 | 0 | 63 |
| 全覆盖版 | 0.0212 | 0.0339 | 0.917 | 0 | 161 |
| 单句式加长版 | 0.0199 | 0.0290 | 1.000 | **2** | 172 |
| **精简版（采纳）** | **0.0190** | **0.0254** | **1.000** | 0 | **124** |

**更短反而更好**，推翻了「词表越全越好」的直觉：

- 全覆盖版把 prompt 里「改 useEffect **的**依赖数组」的句式渗进了正文
  （`tech-02` 平白多出一个「的」）
- 加长版泄漏 2 次
- 起作用的是**点名**，不是上下文

这是 prompt 的第三种副作用形态，前两种是「全角逗号解码成乱码」与
「日常闲话结尾会被模型续写」。

**最终结果**：turbo + 精简版 prompt 在总体 CER 上**超过 large-v3**
（0.0190 vs 0.0207），技术类持平（0.0254 vs 0.0251），同音类更好
（0.0294 vs 0.0363）——而 turbo 快 4.5 倍。

**用户不必付那 4 秒延迟。**

## 四、M5 真正解决的问题

此前每评估一轮转写层改动，都要拉用户读一遍标准文本，迭代速度受限于
用户的时间。

**当天的对比**：上午还在拉用户读六段话，下午就在无人值守下评估了九个
prompt 候选。第二个结论（精简版胜出）**只有基准集才拿得到**——逐个候选
试是试不出「更短反而更好」这个规律的。

## 五、工具

| | 用途 |
|---|---|
| `./scripts/bench-run.sh [模型名]` | 跑全集，出三层指标，报告归档到 `Bench/reports/` |
| `./scripts/prompt-sweep.sh [模型名]` | 一次加载模型跑多个 prompt 候选 × 全集 |
| `./scripts/bench.sh --audio-only` | 重建 TTS 测试音频（`/tmp` 会被系统清空） |
| 菜单栏「开始录制基准集」 | 需 `VINPUT_BENCH=1` 启动，默认隐藏 |

**录制入口默认隐藏**：它往磁盘写音频，而原始设计写明「音频不落盘」。
基准集是那条原则的明确例外，藏起来是为了让例外不被误当成常态。

**对照工具做成门控测试而非独立可执行文件**：它必须跑生产管线才有意义。
测试目标能 `@testable import vInput`，零复刻。`Bench.swift` 的 shim 曾与
生产差两个参数、注释却写着「保持相同」——复刻必然漂移。

**而 M5 自己又复现了一次**（2026-08-17 独立验收 F2）：把 prompt 从 63 字
换成 124 字（提交 036240e）时，shim 里那份副本没跟上，尽管它头顶就写着
「改一处要改两处」。**拿这件事当反面教材写进本文档的同一轮，它又发生了一次**
——注释拦不住复刻漂移。该 shim 已删除，`Bench.swift` 不再复刻任何生产参数，
两条路径都改用不挂 prompt 的 `benchDecodingOptions` 并在注释里写明
「输出不代表生产管线」，质量结论一律由 `bench-run.sh` 给。

## 六、过程中修掉的既有问题

- **`/tmp` 被系统清空导致转写端到端整片失败**，看着像代码坏了。
  `bench.sh` 加 `--audio-only`，此前重建音频得连带跑一遍完整模型对比。
- **录制界面从菜单项改为独立窗口**：菜单里的纯文本渲染成不可交互的说明
  文字，天生小而灰、改字号无效。用户要盯着它连读半小时，看不清就白搭。
  改造中另发现两处：窗口实际尺寸被 SwiftUI 的 fitting size 压掉
  （写的 720×420，开出来 560×352）；正文套 `ScrollView` 后渲染为空。
