# M7 验收清单（蓝牙鼠标接入）

- 日期：2026-08-18
- 设备：`iMouse`（Freqchip 芯片，BLE only，无 HFP/A2DP）
- 协议：服务 `FFF1`，特征 `0783B03E-8535-B5A0-7140-A304D2495CB8`
  （控制帧与音频复用这一个特征，靠长度分流：17 字节控制、128 字节音频）

自动化已覆盖全部可自动化的部分（**762 个单元测试**）：
控制帧解析、会话状态机、两档时长上限与退避、SBC 按包解码、三源互斥、
以及 BLE 字节一路走到 `onFrame` 的端到端接缝。

**剩下必须真机验证的只有三件事**：BLE 能不能连上、按键抑制有没有到位、
以及录出来的中文对不对。**每一条都要用户按鼠标上的键，实现方跑不了。**

### 途中修掉的四个真问题

1. **设备名匹配写成了 `contains`**，把用户旁边另一台 `iMouse2` 当成目标，
   桥连上陌生设备后永远停在「连接中」——而鼠标本身用得好好的（HID 走系统
   栈，与这条 GATT 无关），症状极具误导性。改为精确匹配。
2. **控制帧第 4 字节被当成固定签名**，实际是**电量**（`0x34`=52 恰是当时
   电池特征的读数，几小时后变成 `0x28`=40）。后果不是「少认一个键」，
   是**整个协议随电量下降而失效**，所有帧突然都变成「不认识的帧」。
   原注释的证据是「抓包里 13/13 帧逐字节相同」——13/13 是真的，但那 13 帧
   全来自同一次 40 秒的抓包，电量当然没变。
3. **只按一下的按键会被当成送流**：第三个键发 `0x41` 后不送音频也不发结束
   码，按原处理会挂 30 秒会话，撞线后退订 + 冷却 10 秒——**按一下鼠标，
   鼠标停摆 10 秒**。区分维度错了：该判的不是「多久」，是「有没有音频在流」。
4. **第三个键长按仍会撞上限**：用户明说该键「位置特别不好，容易误碰」，
   于是改成完全不进状态机。

### 逐动作实测的码表

| 物理动作 | 码 | 行为 |
|---|---|---|
| 语音键按住（长按与短按一致） | `0x51` → `0x21` → `0x22` | 听写 |
| 回车键 | `0x27` → `0x28` | 注入 Return |
| 第三个键短按 | `0x41`（单发，无结束码，不送音频） | 无 |
| 第三个键长按 | `0x23` → `0x24` | 无 |
| **未知动作** | **`0x31`** | 持续开麦，30 秒硬上限兜住 |

**`0x31` 的触发动作仍然未知。** 已排除「语音键长按」（实测与短按完全一样）。
它是唯一有真实危害的码——2026-08-18 那次录了 11 分钟环境音。保护是兜底
而非根治：**我们不知道用户什么时候会再撞上**。

## 独立验收（2026-08-18）

**结论：先判「不能合并」，两条阻塞项已修。**

QA 把出货的 `MouseVoiceSession.swift` 拷出来用 `swiftc` 独立编译、按桥的
tick 节奏喂帧，在 `0x31` 保护上实测出两条绕过路径：

| | 现象 | 已修 |
|---|---|---|
| B1 | 设备晚于 3 秒宽限期才送流 → **600 秒仍未退订**，全程零日志 | `0b772b8` |
| B2 | 开始码每 29 秒重发一次 → **600 秒仍未退订** | `0b772b8` |

**B1 的根因正是这个项目反复撞上的那一类**：`silentForeignGrace = 3 秒`
标定自 `0x23`/`0x27`（首包延迟 0.04 秒），而它要保护的 `0x31`
**在抓包里一个控制帧都没有**——首包延迟从未被观测过一次。而测试把
「真实的 0x31 是在送流的」写进注释当前提，于是「全绿」只证明了这个前提
自洽。**对样本成立，对世界不成立。**

另修四条「合并前应修」（`9abb3cf`）：回车键松开码会掐掉听写、跑测试会
真的注入回车键、`KeyPoster` 不清修饰键、诊断路径的名字匹配漏修。

QA 同时验证了若干结论**确实成立**，值得记住：SBC 的 13 条夹具用本机
ffmpeg 逐条重解 13/13 逐字节相同（不是同源伪造）；417 个变异里 404 个被
抓，存活的 10 个是结构性死代码（乘到全零行）；CRC 在现存 2332 帧上
2332/2332 命中；许可证链正确。

## 一、连接（约 1 分钟）

**要做的**：打开鼠标，看菜单栏。

| 检查项 | 期望 |
|---|---|
| 菜单栏出现「鼠标：已连接」 | 与「遥控器：…」并排两行 |
| 显示电量 | 「鼠标：已连接（电量 NN%）」 |
| **遥控器仍然是「已连接」** | 两座桥互不干扰，这条最重要 |

日志里该出现：

```
鼠标 启动 目标名=iMouse
鼠标 连接中 name=iMouse source=retrieveConnectedPeripherals
鼠标 已连接 name=iMouse
鼠标 语音特征已就绪，按住鼠标上的语音键即可听写
鼠标 语音特征订阅成功
```

**若一直停在「搜索中…」**：动一下鼠标让它醒过来（BLE 设备会睡），
每 15 秒会自动重试一轮。仍然不行就把日志发回来——
`鼠标 已连接但没有 FFF1 语音服务` 这一行说明连错了设备。

## 二、听写（主路径，约 3 分钟）

**要做的**：焦点放在一个文本框里（备忘录 / 终端都行），
**按住鼠标的语音键说一句中文，说完松开**。重复三次。

| 检查项 | 期望 |
|---|---|
| 按下时 HUD 弹出，波形在动 | 与 ⌥D 完全一样 |
| 松开后文字注入到光标处 | 中文，标点完整 |
| **输入框里没有杂键垃圾** | 见下面第三节 |
| 说话期间菜单栏没有报错 | |

日志里该出现（一次按键一组）：

```
鼠标 语音键按下，开始录音
鼠标语音键按下，开始录音
会话期间按键 keyCode=NN 抑制=true      ← 见第三节
鼠标 录音结束：收到结束码 0x22
鼠标语音键松开，进入转写
```

**注意有两行相似的「按下」**：前一行带「鼠标 」前缀的是桥（协议层收到
`0x21`），后一行是听写会话真的起来了。**只有前一行说明协议通了但会话没起**
——那多半是被守卫拒了，紧接着会有一行 `鼠标录音被拒：…`，把三个条件的
取值都写出来了。

## 三、按键抑制（要看的就是那个键码）

**这一条是本轮唯一的已知缺口。** 鼠标语音键的 macOS 键码没抓到
（上一轮扫描的 HID 报文只按 report ID 汇总了），所以当前策略是
**会话期间除 `Esc` 外一律抑制**。

**要做的**：在第二节的日志里找 `会话期间按键 keyCode=`，把出现的键码报回来。

- 若**完全没有这一行**：说明鼠标语音键根本不投递键盘事件，
  那么无条件抑制是多余的，应当收窄回 `.only([])` 或干脆不抑制。
- 若有一到两个固定键码：应当把鼠标那档从 `allExcept` 收窄成
  `.only([那几个])`，恢复「录音期间还能正常按键」。

**顺带确认**：按住语音键说话时按一下 `Esc`，本次录音应当被取消
（`Esc` 是逃生口，不在抑制范围内）。

## 四、`0x31` 的保护（本里程碑最重要的一条）

背景：2026-08-18 实测 `0x31`（长按开麦）触发后鼠标**持续送流 11 分钟**，
把用户不知情的房间环境音送了过来。它**没有配对的结束码**。

当前实现：

| 会话类型 | 上限 | 撞线后 |
|---|---|---|
| 语音键（`0x21` → `0x22`） | **90 秒** | 收尾转写已录到的部分，再退订 |
| `0x31` / `0x23` / `0x27` / 未知奇数码 | **30 秒** | 直接退订，**不产出任何文本** |

退订后冷却 10 秒恢复订阅（连续撞线时翻倍，封顶 300 秒），
且恢复后**必须有新的开始码**才会再接收音频。

**要做的（二选一，能复现哪个测哪个）**：

**A. 触发一次 `0x31`**（长按那个功能键，具体是哪个键用户比我清楚）。
30 秒内菜单栏应当变成：

```
鼠标：已超时静音，10 秒后恢复
```

日志里该出现：

```
鼠标 达到会话时长上限，已停止接收音频并退订语音特征，10 秒后恢复订阅
鼠标 语音特征订阅已取消
（10 秒后）
鼠标 冷却结束，恢复订阅语音特征（需要重新按键才会再录音）
```

**这一段期间不该有任何文字被注入，也不该有任何转写发生。**

**B. 按住语音键不放超过 90 秒**。到点应当自动收尾并把前 90 秒转写出来，
日志里是 `鼠标 录音结束：达到时长上限 90 秒`。

> 上限的取舍：**宁可截断一次有意的长录音，也不要默默收一段没人想录的
> 音频。** 若 90 秒在日常使用中被撞到过，说明这个数定小了，报回来调。

## 五、三个源的互斥（约 1 分钟）

**要做的**：

1. 按住**遥控器**的语音键不放，同时按一下**鼠标**的语音键。
2. 反过来再来一次。
3. ⌥D 开始听写期间按鼠标语音键。

每一次都应当：**正在录的那一路不受任何影响**，日志里有一行

```
鼠标录音被拒：模型加载中=false 基准集录制中=false 听写状态=listening
```

（或对称的 `遥控器录音被拒：…`）。

**特别要确认的**：被拒之后，**下一次单独按键仍然能正常开始录音**。
这条是 2026-08-18 修的一个失效链——被拒时若没把协调器状态退回去，
语音键会从此永久失灵。

## 六、扫描诊断的自我保护（可选，仅在需要再抓包时）

```bash
open --env VINPUT_BLE_SCAN=1 dist/vInput.app
```

现在扫描器有**两道**上限：单段连续收流 90 秒，以及**本轮累计 180 秒**。
任一道撞到就自己停下来并告警：

```
BLESCAN ⚠️ 已连续收流 NN 秒且没有结束信号，多半是误触了长按开麦
（鼠标的 0x31 没有配对的结束码）。已自动退订并停止扫描。
BLESCAN ⚠️ 停下来**之前**收到的包已经写进了 <路径>（这道守卫只挡得住此刻
起的新包）。不想留就删掉那个文件。要接着查请重新开一轮。
```

**第二行是新的，而且很重要**：原来的文案写「这段音频不再落盘」，那句话
只对触发的那一个包成立——单段上限 90 秒，触发之前的约 2800 个包早就一个
不少地写进文件了。读到「不再落盘」会以为磁盘上是干净的，而真相相反。

总量上限那一道也是补的：只有单段上限时，「89 秒 + 松 3 秒 + 89 秒 + …」
可以无限累积落盘而守卫一声不吭。

**HID 探针现在也有同一套守卫**，且两条路一起停——它们写的是同一个文件，
只停一条等于没停。探针按 report ID 分开计账（指针报文不能吃掉可能的音频
通道的额度）。

正常用法（按几秒、松开、再按几秒）不会被误伤——空档超过 2 秒就算新一段。

## 独立验收的 P 档，合并前已全部处理（2026-08-18）

九条「可留到后续」用户决定合并前清掉。**七条改了代码，两条只记录**。
逐条理由在代码注释与提交信息里，Roadmap 的 M7 一节有汇总表。

真机这一轮**要额外留意的只有两处行为变化**：

1. **按 Esc 取消录音之后，键盘应当立刻恢复正常。** 之前鼠标档是
   `.allExcept([Esc])` 且取消时不收抑制，按 Esc 之后整个键盘只剩 Esc 能用，
   直到松开鼠标语音键才自愈。第三节顺带确认这一条。
2. **陌生的偶数控制码不再结束正在进行的会话**，只会打一行
   `结束码 0xNN 与本次会话不配对（本次该收 0xNN），已忽略`。
   **这一行出现就说明鼠标上有个键我们还不认识**——看到了请把码报回来。

## 已知缺口

1. **鼠标语音键的 macOS 键码未知**（见第三节）。当前是无条件抑制，
   拿到键码后应当收窄。
2. **`0x31` 到底是哪个键触发的，用户比实现方清楚。** 若第四节的 A 复现不出来，
   B 也能验到同一条上限机制的另一半。
3. **不发写入命令关麦。** `…CB8` 可写，但没有已知的停止命令字节；为了试它
   去猜可能让设备进入未知状态，收益只是省掉一次退订。当前只做本地侧停止
   （不再喂样本 + 退订）。
4. **`0x23` / `0x27` 那两个功能键仍会短暂开麦**（实测零点几秒）。
   实现上它们不启动听写、音频一个字节都不往下送，但设备侧的麦克风开没开
   我们管不了。
5. **`0x43` 的归属是猜的**（P8，只记录不改）。码是真的——`vInput.log` 里
   出现 3 次，全在 16:08 那一段，每次都在一次真回车之前 0.7 / 1.3 / 1.9 秒；
   40 秒抓包里一次都没有。是第四个键、还是回车键的前置沿、还是伸手时蹭到
   的另一个键，**没有证据能分辨**。当前按 `.ignored` 处理（对不认识的码
   最安全的默认值）。要给它接功能，得先有「按哪个物理键会发它」的实测。
6. **⌥D 可能能结束别的源正在进行的会话**（P6，只记录不改）。
   **高置信推断，未实证**：`toggle()` 的 `.listening` 分支确实没有「谁拥有
   这次会话」的判断；但鼠标档抑制是 `.allExcept([Esc])`，`D` 键很可能在
   会话期间就被吃掉了，⌥D 根本到不了那里。**没有真机日志佐证，不要当成
   已验证的结论。** 真机上若想顺手试：鼠标录着的时候按 ⌥D，看会话是不是
   被结束了。
