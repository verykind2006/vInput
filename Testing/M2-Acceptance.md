| 3 | 音量波形随说话起伏 | |

## 四、双模型实测（决定默认模型）

这是 spec 第九节的附加项。分别在 `turbo` 与 `large-v3` 下各跑短句（约 5 秒）与长文（约 25 秒）。

| 观察项 | `turbo` | `large-v3` |
|---|---|---|
| 短句预览是否跟得上说话速度 | | |
| 长文预览是否明显滞后 | | |
| 松手到出字的实际等待 | | |
| **有预览之后，该等待主观是否可接受** | | |

**默认模型决定：保持 `turbo`**（2026-08-14）

**依据：** 真机各跑一遍长文后，用户判断 `large-v3` 「可用但整体体验效果不好」。

即：实时预览确实削弱了等待的成本，但**没有削弱到足以抵消慢 3–5.5 倍**
的程度。当初推迟决定时的假设「预览可能让 8.7 秒的等待变得可接受」
未被实测支持。

`large-v3` 保留在偏好列表中，菜单栏可随时切换，需要质量天花板的场合仍可用。

> 背景：M1 实测 `turbo` 比 `large-v3` 快 3–5.5 倍（长文 1.58 s vs 8.71 s），但 `large-v3` 准确率明显更高且长文有标点。当时把决定推迟到 M2，理由是**实时预览会削弱等待的成本**——松手前文字已在 HUD 上出现过，再等几秒拿更准的结果，主观感受与盯着空白等完全不同。
>
> 但反过来，预览本身消耗算力，`large-v3` 下增量转写更慢，可能跟不上说话速度。**若长文预览一直滞后，那 `large-v3` + 预览这个组合就不成立**——会同时失去预览和速度。

## 五、流式转写的中文表现

WhisperKit 的流式实现主要面向英文调优，`requiredSegmentsForConfirmation: 2` 等参数对中文是否合适未经验证。

| 观察项 | 结果 |
|---|---|
| 文本转为「已确认」的速度是否合适 | |
| 已确认的文本后来是否仍被改写（不该发生） | |
| 预览文本与最终文本的差距有多大 | |

若确认过慢或过快，调整 `StreamingPreviewEngine` 构造 `AudioStreamTranscriber` 时的 `requiredSegmentsForConfirmation` 并记录。

## 已知的待决项

1. **预览积压降级未实现。** spec 第七节要求「预览落后实时超过 3 秒时降级」，本次**有意未实现**，`HUDViewModel.previewDegraded` 字段已预留但无人置位。理由：阈值需要第四节的实测数据才能定准。若实测发现 `turbo` 下从不积压，该逻辑就是过度设计。

2. **`Package.swift` 仍用本地路径依赖** `vendor/WhisperKit`（M1 遗留，因网络丢包）。网络好转后应改回版本化远程依赖。

3. **模型路径解析仍是开发期布局**（M1 遗留），正式分发需改为应用支持目录。
