### 为什么「开与关的结果必须不同」这条格外重要

第一轮 QA 指出：原有三条断言里有两条（「不翻译英文术语」「正确的句子不被
改动」）在**校正压根没跑**时也会通过——管线原样返回时同样成立。

这不是理论担忧。真机首跑时校正确实完全没生效，而那两条正是通过的两条。
若没有补上这条对照断言，我们会看到「3 条里 2 条通过」而误以为基本没问题。

## 二、只有真机才暴露的三个问题

这三个都不是「代码写错了」，全部单元测试在它们存在时照常全绿。

### 1. 我们写的提示词一个字都没送到模型

mlx-swift-examples 2.29.1 的缺陷：`ChatSession` 的 init 把 `instructions`
存进 `messages`（`Streamlined.swift:43`），而 `respond(to:)` 与
`streamResponse(to:)` 都是 `generator.messages = [.user(...)]`
（`:196` / `:237`）——**赋值而非追加**，每次调用把系统消息整个冲掉。

真机表现：模型返回 164 字的闲聊——「小米耀空气可能是指小米推出的某款
智能设备……」，一条替换都没有。修法是把规则并进用户提示，不依赖上游行为。

**这个缺陷不以任何错误形式暴露，只表现为「校正好像没用」。**

### 2. SwiftPM 命令行无法编译 Metal 着色器

mlx-swift 自己的 README 写明了这条限制。`swift build` 不编译、不警告、
照样报 `Build complete`，产物里却没有 `default.metallib`，MLX 一初始化就崩。

后果曾波及两处：
- `scripts/build-app.sh` 打出的 `.app` 里没有 metallib，用户开启校正
  说第一句话就崩——而开发机上跑测试一切正常，因为测试从 DerivedData
  里跑，bundle 就在二进制旁边
- 端到端根本跑不起来

修法：打包与端到端一律走 `xcodebuild`，并在缺 metallib 时**直接失败**
而不是打出一个会崩的包。

### 3. 环境变量与 Metal 构成死锁

`xcodebuild test` 不把父进程环境变量传给测试运行器（`TEST_RUNNER_` 前缀
对 SwiftPM 包同样无效），实测是整个套件被静默跳过、而 xcodebuild 照样报
`TEST SUCCEEDED`、退出码 0。

而 `xcodebuild` 恰恰是唯一能编译 Metal 着色器的方式——**能传环境变量的
构建方式跑不了 MLX，能跑 MLX 的构建方式收不到环境变量，两边都显示绿色。**

修法：门控改用标记文件（`Testing/.e2e-enabled`），不经过任何进程间传递。

另：Swift Testing 默认并行执行，多条用例同时向同一个 MLX 模型推理会让
Metal 崩溃（`commit an already committed command buffer`）。崩溃后
xcodebuild 会重跑一次、跑 0 条用例、报 `passed`——只有退出码 65 露馅。
端到端套件因此加了 `.serialized`。

## 四、未修项（已评估，不阻塞）

1. **闸门可被四类改写绕过**（QA I2）：整句罗马化、全角/半角句号、
   CJK 旁空格、ASCII 大小写。罗马化需要模型主动吐出整句拼音，现实概率低；
   其余三类属于「改了但语义无害」。
   **但设计文档中「结构上不可能重写句子」的说法应订正为「概率上不常见」**
   ——那句话现在不准确。
2. **`apply` 对着已改写的中间结果匹配**（QA I3）：与设计文档「必须在转写中
   原样存在」不符。同音传递性使危害有界（结果仍与原文同音）。
3. **每次开关/换模型都新建 `MLXCorrector`**（QA I6）：旧实例的加载无人取消，
   两份模型可能同时驻留。设计文档主动邀请换更大的模型，这条路径是被推荐的。
4. **没有「本次未校正」的可见反馈**（QA O1）：最常见的情形是「模型还在后台
   加载 → 静默注入原文」，用户无从判断是没加载完、没解析出替换、还是被
   闸门拦了。设计文档规则二的表格本就要求 HUD 标注。
5. **未指定模型目录时静默尝试从 Hugging Face 下载**（QA O2）：无进度、
   无报错、无 UI，且本机网络下这类拉取会失败。
6. **`correct()` 不响应调用方取消**（QA N2）：当前无人取消 `process()`，
   线上不触发；将来若给「校正中」加取消会是个静默 3 秒的坑。

## 五、待人工验收

**自动化只能证明「代码按设计工作」，证明不了「校正好不好用」。**
以下需要实际使用：

```bash
./scripts/build-app.sh
open dist/vInput.app
```

> **首次运行需重新授权**：ad-hoc 签名的指纹随每次构建变化，macOS 会
> 作废辅助功能与输入监控授权。见 `docs/dev-signing.md`。

| 检查项 | 结果 |
|---|---|
| 菜单栏出现「校正：关」 | |
| 「指定校正模型…」选中模型目录后，菜单显示模型名 | |
| 开启校正，说一句「小米遥控器很好用」，文字正确 | |
| 关闭校正，说同一句，能看出差别 | |
| 开启校正后说话，注入延迟可接受（预计 +0.7 秒） | |
| 说英文术语（如「改成 useEffect」），术语未被翻译 | |
| 说一句本来就正确的话，没有被改坏 | |
| 首次开启校正时，前几句因模型加载而未校正——是否可接受 | |

最后一项对应未修项 4：模型加载需要几十秒，加载完成前每次校正都直接注入
原文，而**界面上没有任何提示**。这是当前最可能让人困惑的地方。

日志中每次校正记录 `校正 采纳=[…] 拦下=[…]`，可据此判断闸门松紧：
拦下的条目里若有本该采纳的，说明过严；采纳的条目里若有改坏原意的，说明过松。

## 结论

- **M4 验收标准是否达成**（同一句话开关校正能看出差别）：
  **自动化层面已达成**，真机端到端 6 条全过，「小米耀空气」确实变成
  「小米遥控器」。**产品层面待人工验收**——识别质量好不好用，只有实际
  用过才知道。
- **千问 4B 是否够用**：单条用例证明它认识「小米→遥控器」这个搭配，
  但样本量为一。若日常使用中发现常识不足，菜单里可换更大的模型，无需改代码。
- **性能**：单次推理 0.67–0.80 秒，注入延迟增加不到 1 秒。
- **对 M5 的影响**：润色（标点、口水词、书面化）并入 M5，与场景风格一起做。
  M4 建立的接缝（`Corrector` protocol + 闸门在实现之外）可直接复用。
